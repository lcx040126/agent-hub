Agent Hub 产品更新记录

记录规则
1. 只记录我们在对话中已经明确确认要实施的更新点。
2. 尚在讨论、未复现或未确认的想法不进入正式待更新清单。
3. 每项记录包含目标、验收标准和当前状态；实施完成后补充验证与版本信息。
4. 发布前以本文件中的未完成项目为范围核对，不擅自扩大改动。

待更新项
1. 按风险等级处理重叠范围
目标
- 默认策略下普通代码范围重叠只产生普通警告，不因“自动领取后强制锁定范围”而统一升级为阻止写入；房主可以通过文件风险策略改变具体分类、扩展名或路径的结果。
- 默认策略下只有命中关键文件或关键项目范围时才阻止写入，实际结果以房间当前生效的文件风险策略为准。
- 所有被识别为 Luban 表相关的源文件、生成文件和目录默认只产生普通警告，团队使用现有冲突合表工具处理内容冲突；房主可以通过房间文件风险策略将 Luban 分类改为红色阻塞。

验收标准
- 默认策略中的普通范围重叠返回 warning，相关成员能够看到警告和重叠路径，系统保留冲突记录，但警告本身不阻止继续写入。
- 当前策略标记为红色的范围重叠返回 blocking/deny，并在写入前阻止后来的 Agent。
- 新建或尚未自定义策略的房间中，Luban 范围返回 warning；房主将 Luban 分类改为红色后，后续具体文件检查按 blocking/deny 处理。
- 实际写入具体文件时重新判定风险，避免宽泛目录租约掩盖关键文件类型。

当前状态
- v0.2.0 已实现；自动化与发布候选验证见文末“v0.2.0 发布验证”。

2. 房主控制关键范围阻塞模式
目标
- 房主拥有一个“关键范围阻塞保护”开关，用于在协作频繁时减少不必要的阻塞。
- 开关开启时，按照房主当前配置的文件风险策略，将范围重叠处理为黄色警告或红色阻塞；Luban 默认黄色，但允许房主改为红色。
- 开关关闭时，自动工作租约和普通工作范围的所有文件、目录重叠都只产生黄色警告；成员主动创建的手动独占租借仍保持红色阻塞并要求租客批准。

验收标准
- 只有房主可以切换该模式，管理员和普通成员只能查看当前状态。
- 开启时严格按照房间当前文件风险策略处理 warning 与 blocking/deny，并让所有成员看到生效中的策略版本。
- 关闭时自动工作租约和普通工作范围不得返回 blocking/deny，Agent 可以在记录 warning 后继续；手动独占租借不受该开关影响。
- 切换立即影响后续领取与写入检查，不删除现有租约；界面向全体成员明确显示当前保护模式。
- 每次切换记录操作者、时间和新状态，关闭保护时显示明确风险提示。

当前状态
- v0.2.0 已实现；自动化与发布候选验证见文末“v0.2.0 发布验证”。

3. 历史功能自动记忆与修改确认
目标
- 一项功能完成后，Agent Hub 自动形成可长期复用的功能记忆，使后来开发相关系统的 Agent 能读取已有行为、实现位置、约束、依赖和验证证据，并默认保留这些行为。
- 后续任务明确影响已有功能时，在实际写入前停止操作，由 Codex 在当前对话中列出影响并询问当前成员是否确认修改；只有得到明确确认后才允许在批准范围内继续。
- 历史功能保护与实时租约冲突开关相互独立，关闭关键范围阻塞保护不能绕过历史功能修改确认。
- 功能记忆采用分层检索与自动懒加载，不在每次会话开始时把房间全部历史注入 Agent 上下文；成员无需手工搜索或选择记忆。

功能记忆内容
- 功能名称、所属系统、目标和已经实现的用户行为。
- 不应被意外改变的行为契约、约束和兼容要求。
- 关联文件、类、方法、公开接口、Unity 资源、配置、依赖系统和关联测试。
- 开发成员、Agent 会话、起始 Git 基线、最终提交或未提交状态、实际变更路径和代码差异依据。
- 验证命令、测试结果、运行证据、剩余风险和后续修改历史。

生成规则
- 功能记忆由 Agent Hub 在编码任务完成时自动生成，不要求用户手动填写业务记录。
- 生成结果必须结合任务目标、Agent 结构化总结、真实 Git 差异、实际写入路径、代码符号、依赖分析和验证结果交叉核对，不能只相信自然语言总结。
- 证据不足、没有测试或尚未提交时必须明确标记为待验证或草稿，不能声称功能已经得到完整验证。
- 后续修改形成新的功能版本并保留旧版本历史，不直接覆盖原记录。

版本与当前有效记忆视图
- 功能记忆以“系统 + 具体功能 + 行为契约”为版本单位，不以“成员 + 整个系统”为覆盖单位；同一成员后来修改同一系统中的另一个功能时，不得删除或替代旧功能记忆。
- 每次修改生成不可变的功能修订记录，并在其上维护一个可快速查询的“当前有效记忆视图”；普通任务默认只读取每项功能当前有效的版本，旧版本不进入普通上下文。
- 新修订必须明确标记与前一版本的关系：新增、扩展、替代、废弃、回滚或冲突。新增功能与原功能并存；扩展和替代只更新对应功能及受影响的行为契约。
- 新版本未明确改变的既有行为、约束和兼容要求必须继承到当前有效视图；如果系统无法判断是否仍然有效，应标记为冲突或待确认，不能因新摘要没有提及就自动删除。
- 成员身份和记录时间只作为证据，不作为版本生效依据；“同一个人最后一次修改”或“时间最新”不能自动取得权威地位。
- 未完成、未关联可靠 Git 证据、验证失败或仍位于未确认分支的修订保持草稿或候选状态，不替换当前有效版本。
- 完成状态、Git 提交与分支证据、相关验证结果均符合要求后，修订才能晋升为当前有效版本；缺少必要测试时保持待验证，除非当前成员明确确认接受该验证缺口。
- 不同分支或不同成员对同一行为产生互斥修改时进入冲突状态，保留双方候选，不能按时间先后自动选择；合并或明确确认后再生成新的当前有效版本。
- 回滚操作创建一条新的回滚修订并重新激活被恢复的行为契约，不删除被回滚版本；废弃功能保留废弃原因和替代方案。
- 系统级当前摘要由各项功能当前有效版本组合生成，而不是由某位成员最后一次修改整块覆盖；历史修订继续保存在数据库中，只在排错、回滚和审计时按需展开。

上下文分层加载与预算
- 会话启动层只注入实时租约与阻塞、当前规则、未解决高风险和相关功能记忆的索引摘要，总预算目标为 2,000 至 3,000 token；必须按完整条目裁剪，不能用字符串硬截断破坏内容。
- 任务规划层根据任务目标、当前或预计修改路径、系统标识、类、方法、公开接口、关联测试和依赖关系综合检索，只自动返回相关性最高的 5 至 8 张功能记忆卡。
- 每张记忆卡只包含功能名称、一句核心行为契约、关键符号与路径、验证状态、最新版本标识和命中原因，不携带完整 Git 差异、日志或历史证据。
- 相关性不确定时采用方案 A：先向 Agent 返回候选功能标题和命中原因，由 Agent 自动进行第二次查询；不把低置信候选的全文一起载入，也不要求成员手工选择。
- Agent 确认相关或发现新的实际路径、类与方法后，自动懒加载 1 至 3 项功能的必要详情；规划时取行为与约束，写入前取符号和兼容要求，验证时取关联测试。
- 完整 Git 差异、旧功能版本、测试日志和审计证据只在修改确认、回归验证或人工审计时按需读取，不进入普通任务上下文。
- 默认只检索“当前有效记忆视图”中的功能摘要；相关草稿、候选和冲突仅以简短状态提醒出现，旧版本永久保留用于追溯，但只有沿版本链明确查询时才展开。
- 同一 Agent 会话按功能记忆 ID 和版本缓存已加载内容，后续 Hook 或 MCP 调用不重复注入；记忆版本变化时只发送增量和新的版本标识。
- `session_open` 不再返回房间全量历史；上下文查询必须支持索引、摘要、完整详情等级，以及全局条数或 token 预算、分页游标和命中原因。
- 没有已知路径时先根据任务目标返回少量候选；发现具体路径或符号后自动重新检索，禁止因查询条件为空而返回每类最多数百条全量记录。

影响判断
- 采用类、方法、行为契约和关联测试的组合判断，而不是仅凭文件路径重叠。
- 在同一文件中新增与已有功能无关的代码时，通常不触发修改确认。
- 修改被功能记忆关联的方法、公开接口、行为约束或测试，或者系统无法确定是否影响时，必须触发确认流程。
- Unity 序列化资源等无法可靠进行符号分析的内容可以退化为资源或路径级判断，并明确说明触发原因。
- 写入前影响检查在服务端使用完整功能索引进行精确路径与符号匹配，即使某项记忆没有提前载入 Agent 上下文，也不能因此漏过已有功能保护。

确认流程
- 写入前 Hook 发现历史功能影响时，先拒绝本次写入并把功能名称、既有行为、受影响符号、路径和判断原因提供给 Codex。
- Codex 必须在当前成员的对话中询问是否确认修改；由当前正在执行任务的成员确认，不要求原开发者或房主在线批准。
- 用户明确同意后，通过 MCP 登记一份仅绑定当前会话、功能版本、目标符号和路径的临时授权；授权在会话结束或范围变化后失效，不能作为永久绕过。
- 用户拒绝或没有明确回答时不得修改原功能，Agent 应改用新增接口、扩展点或其他兼容方案。
- 获得授权并完成修改后，必须重新运行关联回归测试，并更新功能记忆的新版本、验证结果和变更原因。

验收标准
- 完成一个包含多个行为的功能后，房间中自动出现一条可查询的结构化功能记录，并能追溯到真实代码、会话和 Git 证据。
- 同一成员先完成某系统的功能 A、后来又新增功能 B 时，A 与 B 分别保留在当前有效视图中，B 不会因时间更新覆盖 A。
- 修改功能 A 形成并验证新版本后，普通查询只返回 A 的新有效版本，旧版本仍能通过版本历史读取；未改变的行为契约会继续保留。
- 未提交、验证失败或分支尚未确认的功能修订只显示为草稿或候选，原稳定版本继续作为当前有效版本。
- 两个分支对同一行为产生互斥修改时不会按时间自动覆盖，而是显示冲突，直到合并或当前成员明确确认新的有效版本。
- 执行回滚后，普通查询读取恢复后的行为，版本历史仍能看到被回滚版本、回滚原因和对应 Git 证据。
- 后续成员开发同一系统时，其 Agent 在规划和写入前自动取得相关功能记忆，无需成员主动搜索或重复说明。
- 房间拥有至少 100 项功能记忆时，新会话启动上下文仍保持在约定的 2,000 至 3,000 token 预算内，且不会返回全部功能正文。
- 规划阶段最多自动取得 5 至 8 张相关记忆卡；低置信候选只显示标题，确定相关后每次只懒加载 1 至 3 项必要详情。
- 同一会话重复检查未变化的功能时不会反复注入相同正文；功能产生新版本后只收到版本变化和必要增量。
- 一项未被启动摘要选中的功能在写入路径或符号命中时，仍会被服务端影响检查发现并触发相同的修改确认流程。
- 修改同一文件中的无关代码不会误触发确认；触及已记录的类、方法、接口、行为或关联测试时会在写入前触发对话确认。
- 未确认时写入保持阻止；确认后只有批准的当前会话、功能和范围能够继续。
- 修改完成后原功能的关联测试会重新执行，功能记忆保留前后版本和批准记录。

当前状态
- v0.2.0 已实现；自动化与发布候选验证见文末“v0.2.0 发布验证”。

4. 阻塞后的自动释放申请与可调租期
目标
- 成员因关键范围重叠被红色阻塞时，Agent Hub 自动向冲突租约持有人发送释放申请，不要求被阻塞成员再手动操作。
- 租约持有人通过 Windows 桌面通知和 Agent Hub 应用内对话框及时得知申请并处理，申请与结果同时进入共享协作记录。
- 自动租约的默认无活动过期时间从 30 分钟调整为 10 分钟，并允许房主按房间调整。

释放申请流程
- 只有 blocking/deny 冲突自动产生释放申请；普通 warning 不产生申请。房主关闭关键范围阻塞保护后，自动租约和普通工作范围不产生申请，但手动独占租借仍保持阻塞并产生申请。
- 申请包含申请成员、任务、冲突租约、重叠路径、阻塞原因、申请时间和租约剩余时间。
- Agent Hub 桌面程序正在运行或位于托盘时，租约持有人收到 Windows 原生通知；应用内同时显示可处理的持久化申请。
- 租约持有人可以选择“交出范围”“暂不释放”或“查看详情”，拒绝时可以附加原因。
- 手动独占租借采用单独的批准语义：租客批准后结束整份独占租约，不提供临时授权或仅交出重叠子范围的选项。
- 同一申请成员、冲突租约和重叠范围的重复请求自动合并并设置提醒冷却时间，避免连续弹窗。
- 成员离线或应用关闭时申请保存在房主数据库中，下次连接后显示；系统不得把“没有及时看到通知”当作已经同意。

范围交接规则
- “交出范围”必须在服务端以单个事务完成冲突范围释放和申请人领取，避免释放窗口中被原成员或第三方重新抢占。
- 第一版交出完整的冲突租约路径；一个租约含有多个独立路径时，只处理发生冲突的路径，其余路径继续保持租约。
- 上述按冲突路径交接适用于自动租约和普通工作租约；手动独占租借按第 7 项处理，批准一次即结束整份独占租约。
- 原 Agent 在下一次 Hook 或续期时必须收到范围已交出的状态，不能继续把本地旧租约当作有效保护。
- 申请人收到同意通知后，其下一次写入检查自动识别已经取得的范围；拒绝或仍待处理时继续保持阻塞。
- Windows 通知只是提醒入口，最终状态以房主服务中的持久化申请和租约事务为准。

租期设置
- 房主可以在房间管理中将自动租约无活动过期时间设置为 5、10、15、30 或 60 分钟，默认值为 10 分钟。
- 只有房主可以修改租期；管理员和普通成员只能查看当前设置。
- 设置变化对新租约和下一次续期生效，不突然截短已经领取的有效租约。
- Agent 工作期间约每 2 分钟发送会话心跳并自动续期；普通状态只在最近 5 分钟发生过真实 Hook 活动时保活，已经开始的单次写入可在长时间构建、测试或 Unity 运行期间保活，但最长 2 小时。
- 超过对应保活上限，或 Agent Hub、Codex、网络、成员客户端停止心跳后不再续期，租约在房间配置的无活动时间后自动过期，避免异常退出永久占用范围。
- 房主修改租期时记录操作者、旧值、新值和时间，并向房间成员显示当前租期策略。

验收标准
- 制造一个关键范围阻塞后，系统自动且只创建一条释放申请，租约持有人的桌面和应用内都能看到完整信息。
- 自动租约或普通工作租约持有人同意后，冲突路径原子交接给申请人；手动独占租客同意后，整份独占租约结束并把申请人的实际请求范围原子交给申请人。拒绝后申请人仍被阻止并看到原因。
- 重复触发同一冲突不会连续创建记录或重复弹窗；离线成员重新连接后能看到未处理申请。
- 新房间默认自动租期为 10 分钟，房主能够在规定档位间调整，其他角色无法修改。
- 持续工作的 Agent 在保活上限内超过一个租期后仍因心跳保持租约；停止心跳或超过保活上限后，租约能在配置时间内自动释放。

当前状态
- v0.2.0 已实现；自动化与发布候选验证见文末“v0.2.0 发布验证”。

5. 人工与外部变化不参与 Agent Hub 执法
目标
- Agent Hub 只对能够归因于当前 Agent 工具调用的写入执行租约检查、冲突警告和阻塞，不接管成员手工编辑的文件。
- 人工编辑、Unity 或 IDE 自动保存、以及其他无法归因于当前 Agent 调用的外部变化，不创建租约、不生成房间风险、不触发 uncovered_path、不隔离 Agent 会话。
- 无法归属的变化采用方案 A：只在成员本机保留临时诊断信息，不上传为房间共享记录，也不向房间成员显示黄色警告。
- 外部变化仍视为用户已有工作；Agent 不得因此覆盖、删除或回滚这些变化。

变化归因规则
- 写入前记录当前工具调用的工作区基线、明确写入意图和标准化后的仓库内目标路径；写入后只核对本次工具调用造成的增量，不再把整个 Codex 会话期间出现的所有 Git 变化统一算给 Agent。
- PowerShell 变量、命令开关、参数名、枚举值和普通命令文本不得被当成仓库路径；只有能够标准化到当前仓库内部的真实路径才能领取租约。
- 能够匹配当前 Agent 目标路径的变化归为 Agent 写入，继续执行正常的黄色警告、红色阻塞和历史功能保护规则。
- 由当前 Agent 明确启动且能够识别来源的代码生成、格式化或构建副作用，自动关联到该工具调用；Luban 源文件和生成结果按房主当前文件风险策略处理，默认只警告，命中手动独占租借时仍阻塞。
- 与当前 Agent 的目标路径和已知副作用均无法建立可靠关系的变化归为外部变化，不提交给房间的写入执法接口。
- Codex 主动发出的写命令如果无法解析目标，不得伪装成外部变化绕过保护；系统应在执行前要求明确路径或停止该 Agent 命令。
- 人工与 Agent 同时修改同一个目标文件时无法可靠按行区分来源；只要该文件是当前 Agent 的明确写入目标，仍按 Agent 写入执行保护，并提示保留文件中已有的用户变化。

误判修复
- 修复 PowerShell 路径提取，确保 `$workDir`、`$junction`、`-LiteralPath`、`Directory`、`Junction` 等变量、开关和参数值不会成为租约路径。
- PostToolUse 不再对会话级全部 changedPaths 执行 uncovered_path 检查，只检查本次工具调用可归因的实际写入路径。
- 发现外部变化时不得设置 quarantine；后续 Agent 工具调用可以继续运行。

验收标准
- Codex 会话运行期间，成员手工修改一个不在 Agent 租约内的文件，随后 Agent 修改其他文件时不会产生 uncovered_path、风险记录或会话隔离。
- Unity、IDE 或其他外部程序产生无法归因的变化时，房间中不出现租约、风险或黄色警告，本机诊断能够说明该变化已被排除出执法。
- Agent 实际修改未领取的关键文件时仍会被正常阻塞，不能利用“外部变化”分类绕过保护。
- Agent 启动已识别的生成流程时，相关输出会正确关联；Luban 源文件和生成文件默认只产生警告，房主改为红色或命中手动独占租借时按对应规则阻塞。
- PowerShell 命令中的变量、开关和枚举值不会出现在租约路径中，真实目标文件能够被正确识别。
- 会话开始前已经存在的人工改动，以及会话期间继续发生但并非 Agent 目标的人工改动，都不会被 Agent Hub 隔离或上传为房间风险。

当前状态
- v0.2.0 已实现；自动化与发布候选验证见文末“v0.2.0 发布验证”。

6. 房主自定义文件重叠风险策略
目标
- 把当前写死在程序中的文件类型和项目目录风险分类改为房间级设置，让房主自行决定哪些 Agent 写入重叠只显示黄色警告，哪些显示红色阻塞。
- 新房间提供可直接使用的默认策略；普通成员和管理员无需维护规则，但可以查看当前生效策略和具体文件的判定原因。
- 风险策略只管理实时范围重叠，不影响历史功能修改确认，也不改变手动独占租借的保护强度。

设置与匹配规则
- 设置页提供普通源码、Unity 场景与 Prefab、Unity 序列化资源、项目设置、Git/CI、结构化配置、Luban 等预设分类，每类使用“黄色警告/红色阻塞”分段选项。
- 支持添加自定义扩展名、具体项目相对文件和项目相对目录规则，不要求房主编写正则表达式。
- 匹配优先级为：具体文件、最长匹配目录、扩展名或预设分类、默认黄色；同一优先级不得保存互相冲突的重复规则。
- Luban 分类默认黄色警告，但房主可以改为红色阻塞。
- 只有房主可以保存、恢复默认或删除风险规则；管理员和普通成员只能查看。
- 每次保存生成新的策略版本，记录操作者、时间和变更内容，并立即影响后续领取与实际写入检查，不删除现有租约。
- 每次写入具体文件时使用最新房间策略动态判定，不能只沿用租约创建时保存的旧风险等级；宽泛目录租约不得掩盖内部具体文件的规则。
- “关键范围阻塞保护”开关开启时应用当前策略；关闭时只把自动工作租约和普通工作范围降为黄色，手动独占租借与历史功能修改确认不受影响。

验收标准
- 房主能够把一个预设分类、扩展名、具体文件或目录分别设为黄色或红色，其他角色无法修改。
- 保存后下一次 Agent 写入检查立即使用新策略，并显示命中的规则、判定结果和原因；旧租约不需要重新创建。
- 具体文件规则能够覆盖目录和扩展名规则，最长目录规则能够覆盖更宽泛的父目录规则。
- 新房间中的 Luban 重叠默认只警告；房主改成红色后，同一具体文件重叠会被阻塞。
- 关闭关键范围阻塞保护后，自动工作租约和普通工作范围全部降为黄色，但手动独占租借仍然要求租客批准。
- 策略变更保留可查询的审计记录，所有成员能够查看当前版本，但只有房主能够编辑。

当前状态
- v0.2.0 已实现；自动化与发布候选验证见文末“v0.2.0 发布验证”。

7. 手动独占租借文件与目录
目标
- 升级现有“手动领取工作范围”入口，在同一个窗口中提供“普通工作范围”和“独占保护范围”两种模式，不再创建另一个功能重复的入口。
- 成员可以主动独占一个或多个项目相对文件或目录；租期内其他成员的 Agent 命中该范围时，无论文件类型如何都先红色阻塞并向租客申请。
- 手动独占租借只约束已接入 Agent Hub Hook 的 Agent 写入，不阻止成员通过 IDE、Unity 或其他方式进行人工修改。

租借与时长
- 任一房间成员都可以创建手动独占租借，并在 5 分钟至房主设置的最大时长之间自定义固定租期；房间默认最大时长为 24 小时。
- 手动独占租借使用固定到期时间，不随 Agent 心跳自动延长；租客需要继续保护时必须主动续租。
- 房主只能设置房间允许的最大租期，不能借此直接释放或接管其他成员的有效独占租约。
- 手动独占租借凌驾于房间文件风险分类和“关键范围阻塞保护”总开关，包含 Luban 在内的所有类型都必须向租客申请。
- 重叠的手动独占租借不得同时生效；已有活跃租约覆盖目标范围时，新的独占租借不能直接抢占。

成员与 Agent 范围
- 租客本人名下接入同一房间的 Agent 自动获得该独占范围的写入权限，无需向自己申请。
- 租客本人使用不同 Agent 会话同时命中该范围时显示黄色提醒，但不阻塞；其他成员的任何 Agent 会话仍然红色阻塞。
- 租客离线或 Agent Hub 客户端关闭时，独占租约继续保留到固定到期时间；其他成员的申请持久化保存，不能因租客离线自动批准。

申请与批准
- 其他成员的 Agent 命中手动独占范围时，复用第 4 项的自动申请、Windows 通知、应用内弹窗、去重和离线保存能力。
- 租客可以“批准并结束整份独占租约”“拒绝”或“查看详情”；不提供临时会话授权，也不能只交出重叠文件或子目录。
- 即使申请人只需要修改独占目录中的一个文件，租客一旦批准，整份手动独占租约立即结束，原租约中的其他文件和目录也不再受保护。
- 批准操作在服务端事务中结束整份独占租约，并只把申请人实际请求的范围交给申请人，避免释放窗口中被第三方抢占。
- 租客拒绝或尚未处理时，请求方继续保持阻塞；租约自然到期、租客主动结束或批准申请后，请求方重新检查并继续。

验收标准
- 同一个手动领取窗口可以选择普通或独占模式；独占模式支持文件、目录和 5 分钟至房间上限内的自定义时长。
- 其他成员的 Agent 修改独占目录下任意类型文件时都会在写入前阻塞并自动发送申请，即使房主关闭普通红色保护或目标属于 Luban。
- 租客自己的 Agent 可以直接写入，不同会话只收到黄色提醒；其他成员不能伪装成同一租客绕过检查。
- 租客批准一个单文件请求后，整份独占租约结束，申请人的精确请求范围被原子领取；拒绝后原租约继续有效。
- 固定租期不会被 Agent 心跳延长，达到截止时间后自动释放；主动续租不得超过房主设置的最大时长。
- 手工、IDE 和 Unity 外部修改继续遵循第 5 项，不产生租约申请、风险记录或会话隔离。

当前状态
- v0.2.0 已实现；自动化与发布候选验证见文末“v0.2.0 发布验证”。

8. 所有客户端自动检查并一键更新
目标
- 使用 GitHub Release 作为正式更新源；新版本发布后，房主和普通成员的所有已安装 Agent Hub 客户端都会自动检查并提示，不要求用户手工配置更新清单地址。
- 用户看到新版本提示后，点击一次“立即更新”即可自动完成下载、真实性校验、安装、必要的数据迁移和应用重启，无需重新下载安装包。
- 完整更新桌面程序、房间服务、界面、本地扫描组件、MCP bridge 和 Codex Hook 运行代码，替代 0.1.0 只能切换单个房间服务 `.mjs` 脚本的实验性更新方案。
- 更新不得擅自在成员工作期间自动重启；未点击“立即更新”时只提醒，成员可以选择稍后处理。

检查与提示
- 每个客户端在启动后和运行期间定期检查 GitHub 上的最新稳定版本，房主电脑不负责把安装文件直接推送给其他成员。
- 发现新版本时显示当前版本、新版本、更新说明、下载大小以及“立即更新”和“稍后”操作。
- 所有成员分别在自己的电脑上确认更新；房间中显示成员客户端版本和兼容状态，便于识别尚未更新的成员。
- 协议或数据库变化与旧客户端不兼容时，提示必须更新的原因；兼容版本可以稍后更新并继续连接。

发布与安全
- GitHub Release 工作流除正式安装包外，还自动生成机器可读的更新清单、文件大小、SHA-256 和数字签名，不再依赖房主手工设置 `AGENT_HUB_UPDATE_MANIFEST_URL`。
- 客户端只接受 HTTPS 更新地址，并使用程序内置公钥验证签名，再核对版本、文件大小和 SHA-256；任一检查失败都不得运行下载内容。
- 更新器拒绝版本降级、清单重放、协议不兼容和来源不可信的安装包，不允许远程清单指定任意未签名 `.mjs` 代码直接运行。
- 更新签名私钥只保存在 GitHub Release 工作流的安全凭证中，不进入仓库、安装包或房主数据库。

一键更新流程
- 用户点击“立即更新”后，客户端显示下载和校验进度；失败时保留当前版本并给出可理解的重试原因。
- 校验完成后由独立更新进程关闭 Agent Hub、替换完整安装内容并重新启动到原安装路径，现有房间连接、DPAPI 成员凭证和项目设置保持不变。
- Codex Hook 与 MCP 配置继续指向稳定的安装路径，普通升级不要求成员重新加入房间或重新安装连接；只有确实改变 Hook 命令时才明确提示重新审核信任。
- 普通成员客户端更新只重启本机程序；房主客户端更新时同时安全重启房间服务，其他成员看到短暂重连状态并在服务恢复后自动连接。
- 更新期间现有租约、申请、功能记忆和房间记录保存在房主数据库中；短暂断线不得自动释放租约或把成员工作标记为结束。

数据库与回退
- 房主应用更新前使用 SQLite 一致性备份机制保存房间数据库，不能只复制可能仍处于 WAL 写入状态的主数据库文件；安装目录之外的连接配置和 DPAPI 凭证不得被安装器主动覆盖。
- 数据库迁移必须具有明确的 schema 版本、升级前兼容检查和事务边界；迁移失败时不得启动不完整的新版本。
- 新版本启动后必须通过房间服务、数据库、MCP 和桌面客户端健康检查才算更新成功。
- 恢复守护成功布防后，下载、校验、安装、迁移或启动健康检查失败时恢复上一版本；如果数据库已经迁移且无法向后兼容，同时恢复更新前数据库备份。安装过程中系统重启或新程序完全无法启动的情况保留为明确边界。
- 更新成功后保留版本、时间和结果记录，并清理已确认不再需要的旧暂存包；最近一个可回退版本和数据库备份保留到下一次成功更新。

验收标准
- 发布一个高于当前版本的 GitHub Release 后，未配置任何环境变量的房主和成员客户端都能自动看到同一更新提示。
- 用户点击“立即更新”后无需浏览器下载或重新运行安装包，客户端自动完成更新并重启，重新打开后显示新版本且原房间连接仍然可用。
- 房主更新产生的短暂服务中断后，成员客户端自动重连，原有活动租约、待处理申请和共享记录没有丢失或被错误释放。
- 篡改安装包、错误哈希、无效签名、非 HTTPS 地址、旧版本清单或不兼容协议都会在执行前被拒绝，当前版本继续正常运行。
- 模拟新版本启动失败或数据库迁移失败时，程序和数据库自动恢复到可工作的旧版本，并向用户显示失败原因。
- 用户选择“稍后”时不会被强制重启，Agent 可以继续工作；客户端之后仍会以不打扰工作的方式保留更新提醒。
- 更新后桌面界面、房间服务、本地组件、MCP bridge 和 Hook 运行代码全部来自同一版本，不再出现只更新服务端脚本而客户端仍停留在旧版本的混合状态。

v0.2.1 已确认功能：退出与后台关闭后的接入隔离

目标
- 成员退出房间或通过托盘真正退出 Agent Hub 后，本机 Codex Hook 和 MCP 立即停止连接房间，不再注入上下文、登记活动、提示冲突或阻止写入。
- 普通关闭主窗口只隐藏到系统托盘，后台继续运行；重启后，未主动退出的连接自动恢复，已主动退出的连接保持暂停。
- 保持 v0.2.0 兼容：协议版本继续为 1，数据库 schema 继续为 3，旧 `connections.json` 缺少 `integrationEnabled` 时默认启用，Codex 配置中的稳定 Hook launcher 路径不改变。

连接与运行哨兵
- 本机连接增加持久化 `integrationEnabled`，并使用串行写队列保存暂停、恢复、令牌和连接状态，避免并发写入相互覆盖。
- 桌面后台维护包含实例 ID、PID、运行状态和心跳时间的本地哨兵文件，约每 5 秒原子刷新。
- 哨兵缺失、损坏、PID 已退出、状态为 `stopped`/`maintenance` 或心跳超过约 30 秒未更新时，本机接入视为 inactive。
- inactive 时 Hook 完全静默：不访问服务端、不创建会话、不注入上下文、不警告、不阻塞。
- MCP bridge 先完成本地握手，远端连接按工具请求懒加载；暂停或房间不可用时返回空工具列表，恢复后自动重连并刷新列表。
- MCP 已连接后发生异步断开会立即刷新工具列表；网络、408、429、5xx 自动重试，401/403 停止轮询并显示明确认证或权限错误。

暂停与清理
- 新增幂等 `POST /api/member/pause`，请求包含 `reason`、`cutoffAt` 和 `requestId`。
- `cutoffAt` 只作为客户端请求身份和幂等参数；实际清理边界由房间服务器首次处理时使用服务器时钟确定，避免客户端与服务器时钟偏差造成漏清或误清。
- 服务端鉴权后在单一事务中关闭当时可见的本人会话，释放本人全部活动租约，取消关联释放申请，使相关功能修改确认过期，并写入审计。
- 暂停不删除成员身份、令牌、房间历史、SQLite 数据库或功能记忆。同一 `requestId` 重试不重复执行；参数不一致返回冲突。
- 网络异常时先立即关闭本机接入，再把失败的远端清理写入本地重试队列。重试沿用原 `cutoffAt` 和 `requestId`；队列未清空前禁止 Hook、MCP、后台扫描、Codex 心跳和桌面写请求创建新远端状态，成功后自动恢复。
- 网络超时、断网、HTTP 408、429 和 5xx 为软失败，Agent 写入继续并显示黄色诊断；真实冲突、冻结、认证失败和本机凭证损坏仍阻塞或报明确错误。
- Hook、MCP 和后台扫描使用跨进程在途操作标记；暂停意图先落盘并关闸门，等待登记操作结束后再固定幂等请求参数。存活进程标记不按年龄误删，等待超时后保留持久化意图且不发送不安全的暂停请求，每次远端请求前重新检查连接状态。

桌面生命周期
- 退出房间：只暂停所选连接并清理本人成员状态；重新启动后仍保持暂停，直到主动重新启用。
- 关闭主窗口：隐藏到系统托盘，不停止后台，不释放会话或租约。
- 托盘“退出”：先使全部本机 Hook/MCP 失效，再尝试清理本人会话与租约并停止服务。
- 房主退出：先清理房主本人状态，再停止本机房间服务；数据库和历史保留，其他成员暂时离线。
- 停止房间服务只依据服务端最新当前成员角色；房主转移、旧版无角色连接或角色查询失败时不会依据缓存或界面参数误停服务。
- 更新安装：进入 `maintenance`，暂停 Hook/MCP，但不释放会话和租约；更新失败回退后恢复原先启用的连接。
- 异常崩溃：哨兵最多约 30 秒后使 Hook/MCP 失效；不承诺远端自动释放手动独占租约，普通租约继续按服务端到期规则处理。

连接路由与切换
- 项目身份优先使用真实路径，无法解析时使用绝对路径；Windows 下忽略大小写，嵌套仓库仍以最深匹配的仓库根目录为准。
- 创建、加入、恢复房间统一经过按项目串行的独占激活流程。切换时先关闭旧连接本机闸门、清理旧 Hook 状态并等待在途操作结束，再尽力清理远端成员会话和租约，最后激活目标连接。
- 旧房间离线、超时或返回 HTTP 408、429、5xx 时仍允许新房间激活，并向用户显示远端清理警告；在途操作等待超时则保持连接暂停并要求重试，不能让两个房间短暂同时接管同一项目。

- MCP 使用明确的连接 ID，并与 Hook 的活动 owner 保持一致；扫描、心跳和通知均过滤暂停或已删除连接，扫描按规范化项目去重。

从本机删除房间
- 删除只影响当前电脑，不删除远端房间、共享记录、成员、功能记忆、房主 SQLite 数据库或其他成员数据。

- 所有本机删除操作（包括不同仓库的连接）进入同一个全局串行队列，避免并发读取和写回 `config.toml` 时相互覆盖；只有删除最后一个 Agent Hub 连接且没有其他受管 MCP 时，才清理共享 Hook。

- 高频 `PreToolUse`/`PostToolUse` 只同步保留红色冲突和历史功能修改确认等硬保护；黄色提醒不阻塞写入。

状态机与持久队列
- 数据库 schema 升至 4。会话对外增加 `active -> finalizing -> closed` 状态；`finalizing` 使用一次性 `finalizationId` 限制最终扫描、功能查询/修订和完成操作。
- 进入 `finalizing` 后立即拒绝普通心跳、分支同步、重新基线、新租约、普通扫描、普通功能修订和直接关闭，并取消本会话待处理申请；活动租约保持原状态与到期时间，等待提交的 automatic 只由 completion 或 TTL 释放。
- 队列按会话写入独立 JSON 文件并使用原子创建/替换；只保存连接 ID、会话 ID、仓库路径、基线、归因路径和租约引用，不保存成员令牌或完整 diff。
- 桌面 worker 每 2 秒检查到期任务，使用指数退避重试；网络离线时保留任务等待恢复，本地证据连续失败 5 次后幂等登记一条“会话结束证据未完整生成”风险并关闭会话，避免永久停留在 `finalizing`。
- 最终扫描以 `finalizationId` 建立唯一索引；功能修订重试前查询同会话已有修订；开始、扫描、风险登记和完成均可安全重复调用。

高频 Hook 优化
- `PreToolUse` 不再为每次写入扫描和哈希整个脏工作树，只读取 Git 根目录、当前分支和 HEAD。
- 分支同步、自动租约续期、冲突检查、历史功能影响检查和必要的自动领取合并为一次 `/api/edits/prepare` 请求。
- 明确路径的 `PostToolUse` 只检查本次目标 pathspec 并增量合并本地观察状态；生成、格式化、构建副作用或归因不确定时才回退完整 Git 工作树扫描。
- `SessionEnd` 生成配置固定为 `timeout = 3`，配置测试防止连接房间或更新后再次写回 60 秒。

Stop 与 Git 提交后释放自动租约
- 新增无 matcher、`timeout = 3` 的 `Stop` Hook；先持久化 completion operation ID、turn ID、activity epoch、自动租约和归因路径，再进行限时 Git/网络检查，所有路径都返回 `{"continue":true}`，不保存最后一条助手消息。
- 自动租约增加 `working / awaiting_commit` 阶段。`Stop` 后停止续租；归因改动已完整提交或完全撤销时立即释放，仍有未提交改动时保留到房间现有 TTL，桌面 worker 每 15 秒检查一次并可提前释放。
- 完整性只针对该 Codex 任务已归因路径：staged、unstaged、untracked、任务基线和 HEAD 内容必须形成完整证据。无关提交、部分提交、提交后继续修改、分支变化、归因截断或证据不完整都保留到 TTL。
- 新一轮写入先废止旧完成任务并递增 activity epoch，再恢复续租或重新领取；Stop、恢复和提交完成请求都使用事务、operation ID 幂等与 epoch 围栏，旧检查或响应重试不得释放新一轮租约。
- `SessionEnd` 可独立完成最终扫描、功能记忆和 Hub 会话关闭；等待提交的自动租约继续到提交完成或 TTL 到期。手动普通和独占租约不受影响，Agent Hub 只检测本地提交且不会执行 `git commit` 或要求 `push`。
- 同一成员、房间和 Codex session ID 复用同一个未关闭 Hub 会话；桌面重启继续处理无令牌、无完整 diff 的持久完成队列。
- 正常桌面退出时，有未到期完成任务的连接不发送成员暂停，也不创建暂停重试；其本地完成队列、Hub 会话和该连接的全部远端租约保留到重启后继续检查或各自 TTL 到期。显式退出房间、暂停和删除连接仍完整清理。

问题与边界
- 同一个 Codex 任务重新打开时，旧 generation 可以继续处于 `finalizing`，新 generation 同时建立为 `active`；两者分配不同的 `hubSessionId` 与 `finalizationId`。旧 generation 的心跳、SessionEnd 收尾和 TurnCompletion 任务按身份隔离，不能阻塞、删除或复活新 generation。
- 桌面应用即使在所有连接均暂停时启动，后续激活已有连接或保存并激活连接时，也会幂等启动仓库扫描、Codex 会话心跳和交接申请提醒，无需重启 Agent Hub 桌面应用；重复激活不会创建重复后台任务。
- `SessionEnd` 与 `TurnCompletion` 队列按 operation ID 使用持久化文件锁和原子替换；enqueue、重试和条件删除按同一 operation 串行合并。`TurnCompletion` job 的 `revision` 单调递增（旧格式缺省从 0 迁移），旧 worker 只有在 revision 仍匹配时才能删除，迟到的旧 enqueue/evidence 不能覆盖较新的证据、重试计数或等待状态；损坏条目隔离为诊断，不阻断其他任务。
- 新 Codex 任务的 `SessionStart` 可能没有真实 turn ID，只能先登记回退 turn；首次真实写入若仍使用同一 activity epoch，会被服务端 fence 当作过期请求拒绝。新增受管 `UserPromptSubmit` 在提示提交时提前登记真实 turn 并推进 epoch，`PreToolUse` 保留一次权威恢复，不再要求人工制造 `Stop -> resume`。
- 同一成员的不同会话申请重叠自动范围时，以已经成功登记的活动租约为现有持有者，后来的会话等待，不再创建会反向阻塞持有者的对等冲突。不得在缺少会话 Git 证据时仅按全局创建时间强制取消其他任务。
- 等待会话在本机持久化最近持有租约、会话、路径、到期提示和触发等待的完整申请范围。缓存到期时间只提示重新检查，不能作为持有者未续租或本地清除围栏的证明；只有明确路径覆盖完整原申请并经服务端允许后才清除围栏。本地状态丢失后复用远端会话时，路径未知写入保持拒绝，明确路径网络失败不放行，进入等待按 dirty 处理，避免取消本机未知的远端租约。
- 等待转换在网络请求前写入待同步标记；响应丢失后，后续明确写入和 `PostToolUse` 必须先幂等补发，后台心跳不得续租尚未确认停止的范围。心跳在同一会话锁内重新读取门禁、请求服务端并合并续租结果，锁外旧 working 快照不能越过刚落盘的 pending/blocked。`PreToolUse` 与 `PostToolUse` 也串行更新状态，旧 Post 不能覆盖较新的等待围栏或绕过围栏 prepare。clean 补同步成功即清除本机该会话的旧自动租约缓存，即使幂等响应已为空；passive 围栏本身不停止已确认 working 的其他路径租约心跳。
- `SessionEnd` 先用确定性 finalization ID 写入持久化收尾队列，再在同一会话锁内删除 Hook 状态；若在途心跳占锁，队列记录作为终止标记，使心跳在响应写回前删除状态而不是复活旧文件。后台 finalizer 在移除终止记录前也会同锁清理 connection、hub session 均匹配的旧状态，避免误删同一 Codex ID 后来打开的新会话。
- 房间服务和房主身份仍正常时，仪表盘可能因累积扫描或其他合法大字段超过桌面代理 1 MiB 上限而被界面误报离线。修复为只返回当前成员最近一次扫描摘要，去掉会话和动态中界面不用的大字段；完整风险规则属于不可裁剪核心，待处理申请先按当前持有人查询再应用上限，区段总数来自数据库真实计数。其余可增长列表按 768 KiB UTF-8 预算装入；SQL 窗口或字节预算截断都返回结构化标记，界面显示刷新不完整而不是房间断开。完整证据仍留在数据库和专用查询中，不放宽代理容量保护。

- 仪表盘响应按可操作性排序，先装入当前持有人的待处理申请，再装入租约、冲突、成员和历史区段；轮询响应中的申请省略可能膨胀的 `overlapPaths`。需要完整申请范围和重叠证据时，成员令牌可调用 `GET /api/release-requests?status=pending` 或 `status=all`，完整房间快照仍可通过 `GET /api/snapshot` 获取。

风险颜色与执行决定
- `severity` 只决定界面的黄色普通警告或红色高风险警告；只有服务端明确返回 `decision=deny` 才阻止对应写入或领取。客户端、MCP、Hook 和发布门禁都不得仅凭 `blocking` severity 自行升级为阻断。
- 红色 `blocking` severity 与 `decision=warn` 可以同时出现。界面按 severity 着色，按 decision 显示“已阻止”并计入阻塞数；红色 warn 显示“高风险警告”。
- 实时租约只有 `decision=deny` 才创建释放申请。跨成员既有手动独占仍是纯监测模式下唯一保留的普通写入 deny；同一成员的其他 Agent 命中自己的独占范围时显示红色高风险但允许写入。新建手动独占范围与活动租约重叠时仍可拒绝领取，该拒绝不属于普通写入阻断。

纯监测模式
- 房主关闭写入阻塞保护后，自动租约和普通工作范围进入纯监测：风险规则仍保留黄色或红色 severity，但 decision 为 `warn`，已有自动阻塞围栏解除，非独占释放申请取消。
- 历史功能影响在纯监测模式下只作建议；确认不可用或尚未确认时仍报告风险，但不阻止写入。写入阻塞保护开启时继续执行原确认门槛。
- 切换前所有现有成员都必须上报当前协议 2；界面提前列出旧协议或未上报协议的成员，服务端在保存时再次权威校验。纯监测房间拒绝旧协议或未上报协议的新成员加入。
- 待处理的手动独占申请及各自的 deny 证据在关闭保护后保留；重新开启保护会清理旧模式的普通冲突投影，由下一次实时检查按当前成员、策略和租约状态重建决定。切换时取消的普通申请不会被两分钟冷却记录错误复用，下一次真实拒绝会重新创建可审批申请。

- 根因：MCP 在复用 SessionStart 创建的 `source=codex-hook` 会话时仍按 MCP 自建会话流程调用 `session_close`，关闭了下一轮 Hook 继续使用的 `hubSessionId`；后续写入因此命中 inactive/stale 会话而被拒绝。

- MCP 说明已改为：Hook session 只复用 SessionStart 返回的 ID，不调用 `session_open` 或 `session_close`；结果用功能修订和事件记录登记。只有 MCP 自建 fallback session 才执行 `session_close`。

v0.2.7 已确认更新（已实现源码候选，2026-08-29）

同一任务的自动范围合并与路径提取修正
- 同一 Codex Hook session、任务、分支和 Git 基线下，连续工具调用产生的自动范围合并为一份持续更新的有效租约，不再按每次 `PreToolUse` 调用创建多张并列的“Codex 自动范围”卡片。
- 当前任务已经拥有 Agent 通过 MCP `lease_acquire` 领取的任务范围时，MCP 与 Hook 必须落到同一份 Agent 托管租约，不再同时创建 `standard` 与 `automatic` 两套范围；出现未覆盖但属于同一任务的真实仓库路径时，原子扩展该任务租约的路径并集。
- 路径已被用户从界面手动领取的普通或独占范围覆盖时，只登记当前任务的路径归因和活动证据，不得把人工租约转换为 Agent 托管租约，也不得在 Agent Stop 时自动释放人工范围。
- 自动范围合并后统一续期、到期、完成与释放；界面展示一张任务级有效范围卡片，并可在详情中追溯各次工具调用新增或命中的路径，不能因合并丢失冲突审计证据。
- 修正 PowerShell 写入目标提取：使用可验证的参数和路径语义解析并标准化到当前仓库，只登记真实仓库路径；`(Join-Path)`、`SilentlyContinue`、变量名、命令开关、枚举值和其他表达式片段不得成为租约路径。
- 系统临时目录以及仓库内被任务清理的临时测试日志，只记录为工具调用副作用或本机诊断，不因命令文本误判而生成面向协作成员的独立任务租约卡片。

Agent 托管租约与人工租约生命周期分流
- 修复 MCP 指令要求 Agent 在写入前调用 `lease_acquire`，但该入口未声明租约类型而被服务端默认保存为 `standard`，导致 Hook 后续又创建 `automatic` 租约、任务完成后只释放自动租约而普通租约持续被心跳续期的问题。
- 复用 Codex Hook sessionId 的 Agent 调用 `lease_acquire` 时，创建或更新带明确 Agent 托管来源的任务租约；这类范围与 Hook 自动领取使用同一身份和生命周期。用户在界面手动领取的普通范围继续保持 `standard`，手动独占继续保持 `exclusive`。
- Agent 托管任务在 `Stop` 后进入 `awaiting_commit` 并停止续期；归因改动已完整进入当前分支 HEAD 或完全撤销时自动完成并释放，仍有未提交、部分提交或证据不完整的改动时保留到现有 TTL，用户不需要手动清理正常完成的任务租约。
- `Stop` 的 3 秒宿主预算内只持久化幂等 completion job 和活动围栏；即使 Hook 进程超时、网络请求未完成或桌面端暂时离线，后台 worker 仍必须完成 `working -> awaiting_commit -> released/expired` 收尾，不能让已结束 Turn 继续心跳续租。
- 升级时只对能够由 Hook session、MCP 调用审计和创建来源共同证明为 Agent 领取的旧 `standard` 租约进行托管迁移；来源不明确的普通租约保持人工生命周期，避免误释放用户范围。

实时工作会话定位增强
- “实时工作”中的每个任务在具备关联数据时显示 `Codex Session ID`、`Hub Session ID` 和“当前 Turn ID”，帮助成员明确任务所属的 Codex 对话、Agent Hub 工作会话以及当前对话轮次。
- 卡片默认显示可区分的缩略 ID，提供完整值查看与一键复制，避免长 ID 撑宽任务卡；`activityEpoch` 作为诊断字段放入展开详情，不占用主界面。
- 同一任务跨越多轮对话时保持一张任务卡并更新“当前 Turn ID”；每轮实际工具调用继续保存当时的 Turn ID 和归因记录，不能因当前值更新或任务级租约合并而覆盖历史审计。
- 手动领取、MCP-only 或旧版本客户端未提供 Codex/Turn 标识时，对应字段明确显示“未关联”或“客户端未提供”，不得生成伪 ID，也不得把 Hub Session ID 误标为 Codex Session ID。
- 会话标识仅向已加入房间的成员展示；它们不作为访问凭据，匿名导出与公开诊断信息默认不包含完整 ID。

验收标准
- 在同一任务中依次调用 MCP `lease_acquire`、执行脚本补丁、Unity 测试、`ProjectSettings` collateral 恢复和临时日志清理后，界面最多保留一份对应的 Agent 托管范围，不得同时出现同任务 `standard` 与 `automatic` 租约。
- 上述流程中不得出现 `(Join-Path)`、`SilentlyContinue`、`Directory`、`Junction` 等伪路径，所有展示路径都能解析为当前仓库内的真实文件或目录。
- 后续工具调用新增真实仓库路径时，同一租约的路径并集、到期时间和活动记录正确更新；完成并释放任务时不会遗留同 session 的孤立自动租约。
- 合并只减少同任务内部的重复范围，不削弱跨成员冲突检测；服务端在线明确确认的其他成员手动独占仍按当前房间策略阻止重叠写入。
- 自动化测试覆盖普通租约已覆盖、自动范围连续扩展、并发工具调用、PowerShell 动态路径、仓库外临时文件和任务结束释放；界面回归确认任务级卡片与调用级审计详情一致。
- 自动化测试覆盖 Agent 通过 MCP 领取后由 Hook 扩展、提交完成自动释放、未提交改动保留到 TTL、Stop 三秒超时与离线重试；正常完成的任务不得要求用户点击“完成并释放”。
- 用户从界面创建的 `standard`/`exclusive` 租约不参与 Agent Stop 自动释放；升级迁移对来源不明确的旧普通租约保持保守，不得仅凭存在 `session_id` 就改写其生命周期。
- Codex Hook 任务卡能够同时显示并复制三类完整 ID；提交新一轮用户消息后只更新当前 Turn，不产生重复任务卡，上一轮 Turn 仍能从调用级审计中追溯。
- 手动任务、MCP-only 会话、缺失字段和旧客户端兼容路径具有明确的空值展示；不同 Hub 会话或不同 Codex Session 的并行任务不会被错误合并或串用 Turn ID。

v0.2.7 决定替代与历史保留追加确认（已实现源码候选，2026-08-29）

决定当前视图与替代关系
- 后续成员在团队明确改变既有方案时，新建决定必须显式携带同一房间内当前决定的 `supersedesDecisionId`；替代要求非空判断依据，不根据标题、路径或文本相似度自动推断冲突。
- 新决定保存为 `current`，旧决定原子更新为 `superseded`。旧内容、作者、依据、路径和时间不删除，默认决定计数、协作记录列表及 Agent 相关上下文只使用当前决定，“查看历史”按新到旧展开完整链。
- 界面为当前决定提供“更新决定”入口，预填原标题、内容、路径和依据；已替代决定不能再次作为替代目标。REST 使用 `POST /api/decisions/:id/supersede` 固定旧决定，MCP `event_append(eventType="decision")` 使用精确 `supersedesDecisionId`，二者共用服务端规则；旧服务不支持专用路径时在写入前明确失败，不回退成无关联记录。
- 同一决定最多存在一个直接后继。两名成员并发更新时只有首个事务成功，后续请求返回 `409 decision_already_superseded`，并在可确定时携带当前后继 ID，客户端刷新后要求基于当前决定重试。
- 决定替代只维护团队方案的当前视图，不改变历史功能影响确认：后续代码写入是否暂停，继续由功能修订的路径、符号和行为影响检查判断。

存储、上下文与兼容性
- `decisions` 增加 `status` 与自引用 `supersedes_decision_id`，使用单后继唯一索引约束线性历史；对应 `records(kind="decision")` 投影在同一事务内同步状态，并写入 `decision.superseded` 审计活动。
- 现有决定迁移后统一视为 `current`。包版本继续为 `0.2.7`，protocol 保持 `2`，schema 保持已用于任务级 Agent 租约的 `6`，最低来源 protocol/schema 保持 `1/2`；早期 schema 6 源码候选在重复打开时也必须幂等补齐决定字段与索引。
- 房间上下文导出格式升为 v2，保留决定状态和原始 ID；导入兼容 v1/v2，先建立新 ID 映射，再恢复替代链，并拒绝缺失目标、自替代、环、状态不一致或一个旧决定拥有多个后继的损坏数据。旧版 `accepted` 状态兼容映射为当前决定；v0.2.6 及更早备份中字段完全一致且一一对应的分裂决定/记录 ID 会合并，任一区段超过 500 条时导出明确失败而不静默截断。

v0.2.8 房间重启后的远程清理恢复优化（源码候选，2026-09-02）
- 修复成员异常关机或网络中断后，旧成员暂停请求尚未送达房间服务器时只能看到通用 `cannot reactivate` 错误、需要反复点击且无法判断恢复进度的问题。
- 桌面端将恢复结果结构化为“本机操作收尾”或“远程清理等待”，房间卡显示当前保存的服务器地址、已重试次数、下次重试倒计时、最后失败原因和中文处理建议。
- 失败原因区分服务不可达、请求超时、凭证失效、成员已移除、房间已解散、版本响应不兼容、无效响应、本地恢复记录异常和未知错误；明确不可恢复状态停止后台普通重试，避免无意义请求。
- 新增“立即重试”：只重试当前连接并绕过退避等待，仍复用原有 `requestId`、`cutoffAt` 和清理边界；同一连接的并发点击通过现有持久化队列锁合并，不会重复发送请求。
- 后台仍按最长五分钟的指数退避自动恢复可重试错误。清理成功后界面检测到连接已就绪，再自动执行正式激活和进入房间，无需用户反复点击。
- 旧清理完成前继续保持连接禁用，不启动 Hook/MCP、扫描器或其他接入调度，也不提供“忽略清理并强制进入”；因此延迟到达的旧请求不会误清理重启后创建的新会话和租约。
- `pause-retry.json` 继续使用兼容的版本 1 文档，仅增加可选诊断字段；不新增远程 REST/MCP、数据库字段、protocol 或 schema，protocol 保持 `2`，schema 保持 `6`。
- 房间解散、凭证失效或成员被移除时，界面引导从本机安全移除旧连接并使用房主最新邀请重新加入；不会引导用户手工删除恢复文件。
- 自动化覆盖旧恢复文件读取、诊断分类、固定请求身份、单连接强制重试去重、跨房间隔离、等待期间不激活接入及恢复成功后的正式激活。发布前另修复 pathless 构建/生成命令无意义启动 PowerShell AST、在 Windows CI 冷启动超时时污染保护诊断的问题；真实变化继续由 PostToolUse Git 差异归因。两套 TypeScript 检查、64 个测试文件共 636 项串行测试、生产构建和 `git diff --check` 通过；异常断电、房主 IP 变化和真实双机恢复仍需单独实机验收。

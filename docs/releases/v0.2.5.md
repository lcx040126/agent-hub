# Agent Hub v0.2.5（未发布）

v0.2.5 处理新 Codex 任务首次写入被旧 activity fence 拒绝、同一成员的重叠自动租约互相反向阻塞，以及仪表盘累积扫描详情超过桌面代理响应上限后被误报为房间离线的问题。

本文件是预发布说明。仓库版本已经调整为 `0.2.5`，但当前没有 `v0.2.5` 标签、GitHub Release、正式 Setup、更新清单或签名资产；GitHub `latest` 仍为 v0.2.4。

## 问题修复

### 新任务首次写入与自动租约协调

- `SessionStart` 在没有真实 turn ID 时只能建立回退 turn；真实 `PreToolUse` 到来后若仍使用同一个 activity epoch，服务端会按 fence 拒绝写入。v0.2.5 新增受管 `UserPromptSubmit` Hook，在每次提示提交时提前登记真实 turn 并推进 activity epoch；若该事件缺少 turn ID 或网络登记失败，`PreToolUse` 仍保留一次基于服务端当前 fence 的权威恢复。
- 同一成员的不同 Codex 会话请求重叠自动范围时，已经成功登记的活动租约保持为现有持有者，后来的会话返回明确的等待结果，不再生成会反向阻塞持有者的对等冲突。
- 同一个 Codex 任务重新打开时，旧 generation 可以继续处于 `finalizing`，新 generation 同时建立为 `active`；两者使用不同的 `hubSessionId` 与 `finalizationId`。旧 generation 的心跳、SessionEnd 收尾和完成队列只匹配旧身份，不能阻塞、删除或复活新 generation 的状态。
- 协调不会仅凭全局创建时间、且在缺少该会话 Git 证据时自动取消其他任务。现有持有者释放或租约到期后，等待会话在下一次写入前重新申请。
- 等待会话会在本机持久化最近持有租约、会话、路径、到期提示以及触发等待的完整申请范围。缓存到期时间不能证明持有者没有续租；只有明确路径覆盖完整原申请并经服务端允许后才清除围栏。即使会话 clean、自身租约已被取消，或 `/write-blocked` 同步响应失败，路径未知写入仍保持拒绝。
- 等待转换在请求服务端前先持久化待同步标记；响应丢失时，后续明确写入和 `PostToolUse` 都必须先幂等补发，后台心跳也不会续租尚未确认停止的范围。心跳会在同一会话锁内重新读取门禁、请求服务端并合并续租结果，锁外读到的旧 working 快照不能越过刚写入的 pending/blocked 状态。`PreToolUse` 与 `PostToolUse` 也在这把锁内串行更新状态，旧的工具结束事件不能覆盖较新的等待围栏或绕过围栏调用 prepare。clean 重试即使收到空的幂等响应，也会清除本机旧自动租约缓存；单纯保留 passive 围栏则不会停止已经确认 working 的其他路径租约心跳。
- `SessionEnd` 与 `TurnCompletion` 队列按 operation ID 使用持久化文件锁和原子替换；enqueue、重试、条件删除按同一 operation 串行合并。`TurnCompletion` job 带单调递增的 `revision`（旧格式缺省从 0 迁移），重试或新证据写入会递增 revision，worker 只有在 revision 仍匹配时才能删除；迟到的旧快照不能覆盖较新的路径证据、重试次数或等待状态，损坏条目也只隔离为诊断。
- `SessionEnd` 会先用确定性的 finalization ID 写入持久化收尾队列，再在同一会话锁内删除 Hook 状态；若在途心跳占锁，队列记录作为终止标记，使心跳在响应写回前删除状态而不是把旧状态复活。后台 finalizer 只有在同锁清理匹配的旧会话状态后才移除终止记录，不会误删同一 Codex ID 后来打开的新远端会话。
- 本地状态丢失后复用远端会话时，在服务端尚未返回完整租约清单前将租约归属标记为不完整：路径未知写入直接拒绝，明确路径网络失败也不按普通离线策略放行；随后进入同成员等待时按 dirty 处理，避免把本机未知的远端自动租约错误取消。
- 自动租约新增结构化协调状态，区分正常工作、因未提交改动阻塞和等待提交；后来的会话通过明确的 claim `wait` 结果等待，不创建对等租约。阻塞或等待提交状态不会被界面伪装成正常工作，也不会按正常工作心跳续租。

### 仪表盘大响应误报离线

- 房主身份只决定房间管理权限，不绕过桌面代理的 1 MiB 响应限制。旧仪表盘把最多 500 条本地扫描的完整 metadata 放入周期轮询；扫描记录积累后，即使房间服务和数据库都健康，代理仍会拒绝过大的响应，界面随即显示“正在重新连接房间”。
- v0.2.5 的仪表盘只返回当前成员最近一次扫描的 ID、会话、成员和时间摘要，不再复制历史扫描 metadata；会话与动态也移除界面不用的大字段。待处理申请在 SQL 中先按当前持有人筛选，再应用 500 条展示窗口，不会被其他成员较新的申请挤掉。完整证据仍保存在 SQLite，并继续由快照或专用查询按需读取。
- 仪表盘响应按可操作性排序，先装入当前持有人的待处理申请，再装入租约、冲突、成员和历史区段；为控制大小，轮询响应中的申请省略 `overlapPaths`。需要完整申请范围和重叠证据时，成员令牌可调用 `GET /api/release-requests?status=pending` 或 `status=all`，完整房间快照仍可通过 `GET /api/snapshot` 获取。
- 风险规则会被管理页整表保存，因此始终作为不可裁剪的核心设置完整返回；损坏或异常膨胀到核心预算外时走小型 507，不会把部分规则伪装成完整设置后覆盖数据库。
- 其他可增长列表按 768 KiB UTF-8 响应预算装入。服务端返回数据库真实总数；SQL 展示窗口或字节预算任一处截断都会写入 `partialSections`，界面保留在线状态并明确显示哪些数据暂未完整刷新。非网络的响应或数据契约错误不再直接显示成房间断开。
- 桌面代理继续保留 1 MiB 防护；若损坏数据导致最小核心字段本身也超过预算，服务端返回小型 `dashboard_capacity_exceeded` 错误，不会把超限正文交给代理。修复不靠放宽容量上限掩盖无界响应。

## Codex 连接变化

受管 Hook 从五类增加为六类：

- `SessionStart`
- `UserPromptSubmit`
- `PreToolUse`
- `PostToolUse`
- `Stop`
- `SessionEnd`

升级对账只补齐或修正能够证明属于 Agent Hub、且连接已经明确授权安装的处理器。用户 Hook、其他 MCP 和无法确认归属的相似配置保持不变。配置确实发生变化后需要重启 Codex。

桌面应用即使在所有连接均暂停时启动，后续激活已有连接或保存并激活连接时，也会幂等启动仓库扫描、Codex 会话心跳和交接申请提醒，无需重启 Agent Hub 桌面应用；重复激活不会创建重复后台任务。

## 兼容性与数据库迁移

- 应用版本：`0.2.5`
- 协议版本：1
- 数据库 schema：5
- 最低可读取来源 schema：2

schema 5 在 `leases` 中增加 `coordination_state`。迁移以旧 `automatic_phase` 为兼容来源：已有 `working` 保持工作状态，已有 `awaiting_commit` 回填为等待提交。重复 Codex session 的保守归并会同时更新 `automatic_phase` 与 `coordination_state`，避免升级后 loser 租约被误当作工作中继续续租。

schema 5 的 `sessions_codex_identity_idx` 在 `(room_id, member_id, codex_session_id)` 上使用部分唯一索引，谓词明确为 `codex_session_id IS NOT NULL AND closed_at IS NULL AND finalizing_at IS NULL`。因此同一 Codex ID 的旧 `finalizing` generation 与新 `active` generation 可以并存，但仍只允许一个未关闭且未进入 finalizing 的当前 generation。

迁移目标覆盖已发布 schema 2、schema 3 和 v0.2.4 schema 4，也允许在已经补列但回填未完成的 schema 5 恢复状态上幂等重试。每次迁移都在事务中完成；旧房间、成员、会话、租约、扫描和索引必须保留，并通过 SQLite 完整性与外键检查。

旧客户端不能继续打开已经迁移到 schema 5 的房间数据库。正式发布前仍应保留更新恢复备份；不要卸载 Agent Hub，不要删除 `%APPDATA%\agent-hub`，也不要手工修改房间 SQLite 文件。

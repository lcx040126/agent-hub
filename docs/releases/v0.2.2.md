# Agent Hub v0.2.2 发布说明

> 本说明明确区分已经通过的自动化验证与仍待完成的真实安装、多机和后续热更新验收。未列为通过的项目不得视为已经验收。

> **v0.2.0/v0.2.1 升级要求：** 请从本 Release 手动下载 `AgentHub-Setup-0.2.2-x64.exe`，完全退出 Agent Hub 后覆盖原安装目录。不要在旧客户端内继续点击更新，不要先卸载，也不要删除 `%APPDATA%` 中的 Agent Hub 用户数据。

v0.2.2 聚焦三个直接影响本机日常使用的问题：同一个本地项目不能同时被多个房间接管；不再需要的已保存房间应能从本机完整移除；v0.2.0/v0.2.1 的更新恢复不能正确复制 `app.asar`。

## 本版变更

### 1. 每个规范化本地仓库只有一个活动房间

同一台电脑仍可保存多个房间，也可以让不同房间指向同一个本地项目，但 Hook、MCP、后台扫描、心跳和通知只能由其中一个活动房间驱动。

- 仓库身份使用解析后的规范化路径；Windows 路径大小写和可解析的路径别名不会制造多个 owner。
- 创建、加入或打开一个房间时，连接先以暂停状态保存，再通过仓库级串行切换启用，避免并发操作短暂产生两个 owner。
- 切换房间会先暂停同项目旧房间，清除旧 Hook 会话并尝试清理远端会话、租约和申请，然后再启用所选房间。
- 升级时如果旧 `connections.json` 为同一仓库留下多个活动连接，启动迁移会把这些候选全部暂停，等待成员明确选择，不按保存顺序猜测。
- 嵌套 Git 仓库按最深的匹配根目录路由，父仓库连接不会抢走子仓库任务。

旧房间断网、超时或返回 HTTP 408、429、5xx 时，本机暂停仍立即生效，未完成的远端清理显示警告。所选房间和 Codex 写入不会只因为暂时性网络故障被阻止。认证失败、服务器明确拒绝清理、本机凭证或本地清理损坏仍属于硬错误，不会被伪装成成功切换。

如果异常状态仍让同一仓库存在多个活动候选，Hook 将其作为软失败处理：`PreToolUse` 放行并明确说明本次没有完成跨成员协作检查，`SessionStart` 注入同类警告，后台扫描和通知跳过该仓库。系统不会随机连接某个房间，也不会把歧义误报成真实租约冲突。

### 2. 从本机移除已保存房间

登录页历史列表、当前房间“连接设置”和房间离线错误页都提供“从本机移除”。该操作与“退出房间”不同：

- “退出房间”只暂停连接，保留成员身份、加密凭证和历史入口，以后可以重新打开。
- “从本机移除”删除该连接记录、DPAPI 加密成员凭证、Hook 会话、暂停准备/重试状态和本地操作标记，并清除当前界面的会话指针。
- 在线时先尝试关闭本人的活动会话、释放租约并取消相关申请；房间暂时离线时本机删除仍可完成，但远端状态可能等待服务器恢复或租期到期。
- 该操作不会解散远端房间，不删除共享记录、功能记忆、其他成员数据或房主 SQLite 数据库。
- 删除房主自己的本机连接时，只有服务器刚确认当前成员仍是房主、远端清理已经完成且没有其他活动本机连接仍使用该服务，才停止本机房间服务。
- 本机连接已经删除后，如果房主服务未能立即停止，删除结果仍会成功返回并显示警告；应用退出时会再次尝试停止服务，不会留下无法重试的已删除房间入口。
- 所有本机删除操作（包括不同仓库的连接）通过同一个全局串行队列执行，避免并发读取和写回 `config.toml` 时相互覆盖。

### 3. 精确清理 Codex MCP 与共享 Hook

删除本机房间时，Agent Hub 会读取 `~/.codex/config.toml`，但不会按名称前缀宽泛删除：

- 只有 MCP 名称、当前 `Agent Hub.exe` 命令、完整参数列表和唯一的 `--connection-id <当前连接 ID>` 全部匹配时，才移除该房间的 `agent_hub_*` 条目。
- 其他房间、用户编辑过的同名配置、未知旧版本条目和非 Agent Hub MCP 均保留。
- 只有最后一个可识别的 Agent Hub MCP 被移除、且不存在其他潜在 `agent_hub_*` 条目时，才尝试移除共享 Hook。
- 删除最后一个 Agent Hub 连接时会正确清理仍保持精确受管定义的共享 Hook；只要还有其他连接或潜在 MCP，Hook 就继续保留。
- Hook 删除同样要求命令、前置参数、事件、matcher 和 timeout 与受管定义精确匹配；用户自定义或修改过的处理器保留。
- 实际改写配置前生成新的时间戳 `.bak` 备份并原子替换；配置发生变化时提示重启 Codex。

保守留下无法确认归属的配置比误删用户配置更安全。本机房间数据删除和 Codex 配置清理是两个边界：精确匹配失败不会扩大删除范围。

### 4. 修复 `app.asar` 更新恢复备份

v0.2.0 和 v0.2.1 的恢复准备通过 Electron 主进程中的 `node:fs/promises.cp` 递归复制整个安装目录。Electron 会改写普通 `node:fs`，把路径中的 `.asar` 当作虚拟归档处理。当复制目标到达恢复目录的 `resources/app.asar` 时，目标文件尚未形成有效归档，Electron 却尝试解析它，于是抛出：

```text
Error: Invalid package ...\application\resources\app.asar
```

源 `app.asar` 可以正常解析和计算哈希；使用 Electron 的 `original-fs` 复制同一文件后，源与备份字节一致。因此该错误不是 Codex 占用、安装到 D 盘、源归档损坏或更新安装器下载失败。

v0.2.2 的恢复准备改为：

- 使用 `original-fs` 对安装目录执行物理递归复制；
- 使用物理 `stat` 确认备份中的可执行文件和 `app.asar` 都是实际文件；
- 比较源与备份 `app.asar` 的文件大小和 SHA-256，只有字节一致才写入待恢复计划；
- 使用同一物理文件系统清理恢复备份，避免异常路径再次触发 ASAR 虚拟目录处理。

## v0.2.0/v0.2.1 必须手动覆盖升级

这项修复位于执行更新准备的客户端自身。v0.2.0/v0.2.1 会在启动新安装器和写入 `pending` 恢复计划之前失败，因此已经下载的 v0.2.2 文件无法反向修补仍在运行的旧更新器。

升级到 v0.2.2 时，房主和每位成员都必须完成一次外部 Setup 覆盖：

1. 暂停新的 Agent 写入并退出 Agent Hub。
2. 从正式 Release 下载 `AgentHub-Setup-0.2.2-x64.exe`，核对 `SHA256SUMS.txt`。
3. 运行 Setup 并选择原安装目录覆盖安装；不要先卸载，也不要删除 Agent Hub 用户数据。
4. 启动 v0.2.2，确认原房间、连接、加密凭证和 Codex 接入仍在。
5. 房主先确认原房间可打开，再让成员逐台覆盖并恢复工作。

退出 Codex、重复点击热更新或删除更新缓存不能修复旧客户端代码。完成这一次覆盖后，后续版本才使用 v0.2.2 的物理备份与恢复路径。

## 兼容性与数据边界

v0.2.2 保持 Agent Hub 协议版本 1 和 SQLite schema 版本 3，并继续读取 v0.2.0/v0.2.1 的房间数据库与连接文件。

- 同项目唯一活动房间只约束本机接入选择，不合并或删除远端房间。
- 覆盖安装不应主动删除房间数据库、项目连接、加密凭证、风险策略、协作记录或功能记忆。
- “从本机移除”是成员明确选择的数据删除操作，不属于覆盖安装迁移。
- 网络软失败允许本次写入继续，但表示实时协作检查没有完成，不等于跨成员兼容性已经验证。

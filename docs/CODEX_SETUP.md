# Agent Hub 与 Codex 连接

Agent Hub 安装版可以把已经加入的协作房间连接到本机 Codex。连接完成后，Codex 会通过 MCP 按需读取房间中的实时状态和功能记忆，并通过六类 Hook 在会话开始、提示提交、写入前后、回合停止和会话结束时自动协调工作范围。日常使用不需要手工复制 Token，也不需要为每次任务重复配置；功能完成后的结构化记忆也由 Agent 与 Agent Hub 自动登记。

> 本文适用于 Agent Hub v0.2.5 正式安装版。

## 使用前准备

- 使用 Windows 安装版（文件名包含 `Setup`），不要使用 Portable 便携版完成自动接入。
- 每位成员都要在自己的电脑上准备好该项目的本地 Git 仓库。
- `git` 命令必须已安装并加入系统 `PATH`。如果刚安装 Git，请重新启动 Agent Hub 和 Codex，使新的环境变量生效。
- 房主创建的局域网房间依赖房主电脑上的 Agent Hub 持续运行；其他成员还需要能够访问房主提供的邀请地址。

## 首次连接步骤

1. 安装并打开 Agent Hub。
2. 点击“选择项目”，选择本机对应的 Git 项目目录。房主和成员可以使用不同的本地路径，但应当是同一个项目。
3. 房主选择“创建房间”；其他成员选择“加入房间”，填写房主发来的邀请地址和房间码。
4. 成功进入房间后，打开“连接设置”，在“Codex 自动接入”区域点击“安装连接”。
5. 等待界面提示连接已经安装，然后完全关闭并重新启动 Codex。
6. Codex 第一次加载 Agent Hub 的非托管 Hook 时会要求用户确认信任。确认命令确实指向本机安装的 Agent Hub 启动器后，允许这些 Hook 运行。这是 Codex 的安全确认，Agent Hub 不会也不应绕过它。

每位协作成员都应在自己的电脑上执行一次上述流程。房主安装连接不能代替其他成员的本机安装。

## 安装连接后发生了什么

Agent Hub 会修改当前 Windows 用户的全局 Codex 配置：

```text
~/.codex/config.toml
```

在常见 Windows 环境中，它位于 `C:\Users\<用户名>\.codex\config.toml`。Agent Hub 会保留能够识别的现有配置，并新增：

- 一个名称以 `agent_hub_` 开头的 MCP 服务配置；
- `SessionStart`、`UserPromptSubmit`、`PreToolUse`、`PostToolUse`、`Stop`、`SessionEnd` 六类 Hook；
- Codex 的 Hook 功能开关。

如果 `config.toml` 原本已经存在，写入前会在同一目录生成带时间戳的备份：

```text
config.toml.agent-hub-<时间戳>.bak
```

安装完成后必须重启 Codex，新配置才会在新会话中生效。

## 凭证和通信原理

加入房间后得到的成员凭证不会写入 `config.toml`、PowerShell 脚本或项目仓库。Agent Hub 将凭证保存在自己的本机连接存储中，并使用 Windows DPAPI 加密。通常只有保存凭证的同一 Windows 用户能够解密；不要把 Agent Hub 的用户数据目录当作可跨账号复制的登录文件。

MCP 不经过 PowerShell。对应的 `agent_hub_*` 配置会直接把 `command` 指向安装版的 `Agent Hub.exe`，把安装包 `app.asar` 中的 headless runner、本机用户数据目录和房间连接 ID 放入 `args`，并通过 `env.ELECTRON_RUN_AS_NODE=1` 让程序以无界面的 Node 进程运行。这个进程从本机安全存储读取相应房间凭证，再连接房主的 Agent Hub 房间服务。

Codex 与该进程之间使用标准输入输出（stdio）运行本地 MCP bridge。因此 Codex 配置中不需要出现房间 Token，也不需要直接把远程 HTTP 地址配置成 MCP 服务。

六类 Hook 使用另一条启动链：Codex 调用 Agent Hub 生成的 PowerShell headless sidecar，再由 sidecar 以 Node 模式执行对应 Hook。这个 PowerShell 脚本只保存已安装程序、headless runner 和本机用户数据目录的路径，不包含 Token。

## 六类 Hook 的职责

- `SessionStart`：Codex 会话开始、恢复或压缩后，读取当前仓库、分支和房间实时快照，把规则、活跃租约、未解决风险和少量相关记忆索引提供给 Agent。启动内容按完整条目装箱，目标预算为 2500 token，硬上限为 3000 token，不会把房间全部历史一次性注入。
- `UserPromptSubmit`：每次用户提交新提示时，在任何写入前登记真实 turn ID 并推进 activity epoch。若该提示没有提供 turn ID 或登记暂时失败，`PreToolUse` 仍会根据房间当前 fence 做一次权威恢复；不会要求用户先制造一次 `Stop -> resume` 才能写入。
- `PreToolUse`：在 `apply_patch` 或常见命令行写入前识别目标路径，自动申请尽可能小的工作范围并检查冲突。普通重叠会登记黄色警告后继续；命中房间当前红色风险规则、手动独占范围或未经确认的历史功能影响时，才会暂停该次写入。红色租约冲突会自动生成释放申请。
- `PostToolUse`：写入后读取实际 Git 变更，并只登记能够归属于本次 Agent 工具调用的路径。会话开始前已经 dirty 的文件会使用本地指纹识别后续变化；IDE、Unity、脚本或成员手工产生且无法归属于本次 Agent 写入的变化保留在本地，不会自动领取租约、制造冲突或隔离会话。
- `Stop`：每次 Codex 回合结束时先持久化当前 turn、activity epoch、自动租约和归因路径，再停止这些自动租约的心跳续期。归因改动已经完整进入本地 HEAD 或已经完全撤销时立即释放；否则继续保护到租期到期，并由桌面后台每 15 秒检查提交状态。Hook 始终返回继续，不会保存最后一条助手消息。
- `SessionEnd`：把最终 Git 与验证证据处理排入持久队列，形成或更新功能记忆并关闭 Agent Hub 会话。证据不足的结果保持草稿或候选状态；等待提交的自动租约继续独立保护到提交完成或租期到期。

每次 Codex 会话都会在房间中取得独立的 Agent Hub 会话 ID。Hook 会把这个 ID 提供给同一会话中的 MCP，领取、心跳、写入检查、功能确认、验证、交接和结束操作都会复用它；本地状态丢失后也会按成员、房间和 Codex session ID 找回同一个未关闭会话，不会额外创建重复会话。即使同一成员同时运行多个 Codex 会话，也不能把其中一个会话的租约或历史功能修改授权当作另一个会话的许可。桌面端会为活跃会话发送心跳；普通状态最后一次真实 Hook 活动超过 5 分钟后停止心跳，正在执行的单次写入最多保活 2 小时，防止异常退出后永久续租。进入等待提交阶段的自动租约不再续期，按房间现有租期自然到期；手动普通和独占租约保持各自原有状态与到期规则。

同一成员的多个 Codex 会话请求重叠自动范围时，已经成功登记的活动租约继续作为现有持有者，后来的会话进入等待，不会再反向阻塞持有者。Agent Hub 不会在缺少该会话 Git 证据时仅按创建时间强制取消其他任务；持有者释放或租约到期后，等待中的会话可在下一次写入前重新申请。

进入等待后，Hook 会在本机保存最近持有租约、会话、路径、到期提示以及触发等待的完整申请范围。缓存到期时间只表示适合再次检查，不能证明持有者没有续租；路径未知的生成、格式化和构建写入会一直保持暂停，直到明确路径覆盖完整原申请并由房间服务确认允许。即使等待会话当前没有未提交差异、自己的租约已被服务端取消、复用远端会话后本机还没有恢复完整租约归属，或 `/write-blocked` 同步响应丢失，也不能绕过该保护。明确路径会继续请求房间服务；若存在已知等待、阻塞或尚未恢复的远端租约状态而服务端暂时不可达，本次明确写入也保持暂停，不退回普通断网放行策略。

这些 Hook 安装在全局 Codex 配置中，但会根据当前工作目录匹配已经保存在 Agent Hub 中的本地仓库。对于没有加入任何房间的仓库，Agent Hub 会静默跳过，不应阻止普通 Codex 工作。

从 v0.2.2 开始，同一规范化本地仓库同一时间只允许一个活动房间。规范化会解析可用的真实路径，并在 Windows 上忽略路径大小写，因此同一路径的别名不会获得两套同时运行的 Hook/MCP。打开一个已保存房间时，Agent Hub 会先暂停同项目旧房间的本机接入和远端活动状态，再启用所选房间；旧房间临时离线时，本机暂停仍生效，未完成的远端清理只显示警告，不会仅因网络错误阻止所选房间或 Codex 写入。

升级后的旧连接数据如果仍为同一仓库留下多个活动候选，启动迁移会先把这些候选全部暂停，等待成员明确选择。若异常状态仍导致匹配歧义，`PreToolUse` 会放行并明确提示本次没有完成跨成员协作检查，`SessionStart` 会注入同类警告，后台扫描和通知则跳过该仓库。系统不会随机挑选一个房间，也不会把配置歧义伪装成已经完成保护。

## Portable 便携版限制

Portable 版本允许体验桌面界面，但禁止“安装 Codex 连接”。便携程序通常从临时且可能变化的解压路径运行；把该路径写入 Codex 全局配置后，下次启动很可能失效。

需要自动 MCP 和 Hook 接入时，请安装 Setup 版本，再从房间的“连接设置”点击一次“安装连接”。

## 对 Git 操作的影响

Agent Hub 不会替代 Git，也不会改变日常的 `commit`、`pull`、`push` 操作方式。它通过 Git 读取仓库根目录、当前分支、提交和实际改动，因此 `git` 必须能够从 `PATH` 直接运行。

房间状态和 Hook 主要负责写入前后的协作检查；Git 仓库、项目源码、项目自身规则和测试结果仍然是事实来源。Agent Hub 能降低多人 Agent 互相覆盖和忽略依赖的概率，但不能在没有测试或运行时验证的情况下保证业务语义绝对兼容。

Agent Hub 检查的是当前 Codex 任务已经归因的路径，而不是简单观察 HEAD 是否出现新提交。所有归因路径都必须没有 staged、unstaged 或 untracked 差异，且相对任务基线保留的净改动已经进入当前分支 HEAD；完整撤销不要求空提交。无关提交、部分提交、提交后继续修改、分支变化、路径归因截断或证据不完整都会保留自动租约到 TTL。Agent Hub 只检测本地提交，不会执行 `git commit`，也不要求 `push` 或限定提交作者。

## 黄色警告、红色阻塞与释放申请

- 房间默认将普通代码范围重叠处理为黄色警告；黄色警告会被记录并展示，但不会拦住 Agent 写入。
- 命中房间当前设置为红色的文件规则时，后来者会在写入前被阻塞。Luban 源表、生成文件和相关目录默认只警告，房主可以按团队需要修改。
- 房主可以关闭“关键范围阻塞保护”，让自动租约和普通工作租约的所有重叠都降为黄色警告；手动独占租借和历史功能修改确认不会被该开关绕过。
- 红色租约冲突会自动向租约持有人创建释放申请。持有人可在 Agent Hub 中批准或拒绝；桌面程序运行时还会显示 Windows 通知。普通租约批准后只交接实际冲突路径，手动独占租约批准后会结束整份独占租约，再把申请人的实际路径原子交接给申请人。
- 自动租约默认在 10 分钟无心跳后到期，房主可选择 5、10、15、30 或 60 分钟。手动独占租借使用成员明确选择的固定时长，并受房间最大时长限制。

## 历史功能修改确认

Agent Hub 将实时租约和历史功能记忆作为两层独立保护：租约处理“别人现在正在改什么”，功能记忆处理“以前已经完成了什么”。当服务端根据路径、类、方法、接口、行为约束或关联测试判断本次写入会影响当前有效功能时，Hook 会先拒绝写入，并把受影响内容交给 Codex 在当前对话中询问当前成员。

当前成员明确同意后，Codex 通过 MCP 登记只绑定当前会话、功能版本、符号和路径的临时确认；目标范围或提案变化后必须重新确认。完成修改后应重新验证相关行为并产生新的不可变功能修订。旧修订继续用于审计和回滚，但普通任务只读取当前有效版本。

## 多房间、暂停和从本机移除

每次为一个保存的房间点击“安装连接”，都会创建或更新一个独立的 `agent_hub_*` MCP 配置。多个房间可以保存在历史列表中，但同一规范化本地仓库只有当前明确打开的房间保持活动。

“退出房间”和“从本机移除”有不同的数据边界：

| 操作 | 本机保存记录与凭证 | Codex 配置 | 远端房间 |
| --- | --- | --- | --- |
| 退出房间 | 保留，连接保持暂停，之后可重新打开 | 保留 | 尝试清理本人的活动会话和租约，房间与团队记录保留 |
| 从本机移除 | 删除该连接、DPAPI 加密成员凭证、Hook 会话和本地接入状态 | 精确移除对应 MCP；必要时移除受管共享 Hook | 不解散房间，不删除团队记录、功能记忆、其他成员数据或房主数据库 |

“从本机移除”可以从登录页的已保存房间列表、当前房间的“连接设置”，以及房间离线错误页执行。确认窗口会再次说明它只删除当前电脑的数据。如果房间临时离线，本机删除仍会完成；远端会话或租约可能保留到服务器恢复或按租期自然过期。

清理 `~/.codex/config.toml` 时，Agent Hub 只有在以下身份全部精确匹配时才删除 MCP：`agent_hub_*` 名称、当前安装的 `Agent Hub.exe` 命令、完整参数序列，以及唯一的 `--connection-id <当前连接 ID>`。名称碰撞、用户改过的命令或参数、其他房间 MCP 和非 Agent Hub 配置都会保留。

Hook 是多个房间共享的。只有删除最后一个本机房间，并且配置中已经没有其他可能属于 Agent Hub 的 MCP 条目时，程序才尝试删除命令、参数、事件、matcher 和 timeout 仍与受管定义精确一致的 Hook 处理器；用户添加或修改过的 Hook 不会被扩大匹配删除。任何实际配置改写都会先生成新的 `.bak` 备份，并提示重启 Codex。若精确身份不匹配，房间本机数据仍可删除，但保守地留下无法确认归属的 Codex 配置供用户检查。

卸载 Agent Hub 前，建议先逐个使用“从本机移除”。如果卸载后仍看到失效条目，再完全退出 Codex，检查 `~/.codex/config.toml` 中遗留的 `agent_hub_*` 和命令指向 Agent Hub、包含 `--codex-hook` 的处理器。手工处理时只删除能够确认属于 Agent Hub 的内容，不要直接用旧 `.bak` 覆盖当前文件，否则会丢失备份生成后新增的其他 Codex 配置。

## v0.2.0、v0.2.1 或无法启动的 v0.2.3 手动覆盖升级

v0.2.0 和 v0.2.1 不能依靠应用内更新完成到当前正式版 v0.2.5 的升级。旧客户端使用 Electron 改写过的 `node:fs` 复制恢复目录；当目标路径到达 `resources/app.asar` 时，尚未形成的目标会被当作 ASAR 包解析并报 `Invalid package`。该错误发生在安装器启动之前，不是 Codex 进程、源归档损坏或自定义安装盘符造成的。

修复后的恢复路径使用 Electron `original-fs` 把 `app.asar` 当作物理文件复制，并核对源文件与备份文件的大小和 SHA-256。清理失败备份时也使用物理文件系统，避免再次把 `.asar` 当虚拟目录。

无法启动的 v0.2.3 没有可用的应用内更新入口，也必须手动覆盖 v0.2.5。已恢复或已正常迁移到 schema 4 的 v0.2.3、v0.2.2 和 v0.2.4 可以正常使用应用内更新。

每台仍运行 v0.2.0、v0.2.1 或无法启动的 v0.2.3 的电脑都要完成一次手动覆盖：

1. 暂停新的 Agent 写入，并完全退出 Agent Hub。
2. 从正式 v0.2.5 Release 下载 `AgentHub-Setup-0.2.5-x64.exe`，核对同一 Release 的 `SHA256SUMS.txt`。
3. 运行 Setup，选择当前 Agent Hub 的原安装目录覆盖安装；不要先卸载，也不要删除 `%APPDATA%` 下的 Agent Hub 用户数据。
4. 启动 v0.2.5，确认已保存房间、当前成员、项目路径和 Codex 连接仍在，再让团队恢复工作。
5. 如果本次覆盖改变了 Codex 接入配置，按界面提示重启 Codex。

v0.2.0/v0.2.1 必须由旧客户端外部运行 Setup，因为已经下载的新文件无法反向修补正在执行更新准备的旧进程；无法启动的 v0.2.3 则无法进入应用内更新界面。完成 v0.2.5 覆盖后，后续更新才会使用当前正式版的恢复和数据库迁移代码。

## 常见问题

**点击安装连接时提示必须使用安装版**
当前运行的是 Portable 版本。安装 Setup 版本并从已保存的房间重新点击“安装连接”。

**Codex 启动后没有房间上下文**
确认已经在 Agent Hub 中保存该本地 Git 项目与房间的连接，安装连接后完整重启 Codex，并在首次提示时信任 Agent Hub Hook。

**提示找不到 Git 或无法识别仓库**
确认所选目录是 Git 仓库，并确认在新的终端中可以直接运行 `git`。修改 `PATH` 后重新启动 Agent Hub 和 Codex。

**成员无法连接房间**
确认房主的 Agent Hub 正在运行，成员使用的是房主提供的局域网邀请地址和正确房间码，并检查 Windows 防火墙与局域网连通性。

**应用内更新提示 `Invalid package ...\resources\app.asar`**
这是 v0.2.0/v0.2.1 的恢复备份缺陷。退出 Codex 或重复点击不会修复；请按上面的步骤手动运行 v0.2.5 Setup 覆盖一次。

**拒绝了首次 Hook 信任**
未经信任的 Hook 不会执行，自动领取范围和写入拦截也就不会完整生效。先核对 `~/.codex/config.toml` 中命令指向本机 Agent Hub 生成的 PowerShell 启动器，再按 Codex 的安全流程重新确认。

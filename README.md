# Agent Hub

Agent Hub 是一个面向多人、多 Agent 开发的协作房间。房主创建房间后，所有成员的 Agent 都连接到同一份实时、结构化的项目状态，在写入前检查其他人的工作范围，在功能完成后保留可追溯的功能记忆。

它不会合并不同模型的内部记忆，也不会上传私人聊天或隐藏思考。它共享的是成员、会话、路径、租约、项目结构、功能行为、决定、验证、风险和 Git 证据等可审计信息。

> v0.2.3 是 Windows x64 局域网版本。已安装 v0.2.2 的用户可以使用应用内更新；v0.2.0 和 v0.2.1 用户需要手动运行 v0.2.2 或更新版本的 Setup 覆盖安装一次。房主退出、关机或离开网络时，其他成员会暂时无法同步。

## 工作原理

```text
房主电脑
  └─ Agent Hub 房间服务 + SQLite
       ├─ 保存成员、租约、风险策略和释放申请
       ├─ 保存不可变的功能修订与当前有效功能视图
       └─ 通过 REST/MCP 向房间成员提供同一份状态

每位成员的电脑
  ├─ Agent Hub：加入房间、显示通知和管理连接
  ├─ MCP：让 Codex 按需查询上下文和执行协调操作
  ├─ Hooks：在会话开始、写入前后、回合停止和会话结束时自动检查
  └─ 本地扫描器：分析 Git、C# 和 Unity 依赖，只同步结构化元数据
```

Agent Hub 主要解决两类不同的问题：

- **正在开发的工作冲突**：使用限时租约、黄色警告、红色阻塞和释放申请协调。
- **已经完成的功能被后来任务意外改坏**：使用功能记忆、影响判断和当前会话内的明确修改确认保护。

这两套保护彼此独立。房主关闭普通红色阻塞后，手动独占租约和历史功能修改确认仍然有效。

## 安装

1. 打开 GitHub 项目的 **Releases** 页面，下载 `AgentHub-Setup-版本号-x64.exe`。
2. 核对同一 Release 中 `SHA256SUMS.txt` 的文件哈希，再运行安装程序。
3. 团队中的房主和每位成员都要在自己的电脑上安装。大家使用同一个 Setup 安装包。
4. 当前安装包没有商业代码签名证书。Windows SmartScreen 弹出提示时，应先确认下载来源和哈希；来源不明或哈希不一致时不要继续。

v0.2.3 继续使用 NSIS Setup 安装版，不发布 Portable 便携版。安装目录可以在安装过程中选择，房间数据和本机连接数据保存在 Windows 用户数据目录中，不会因为覆盖安装新版而主动删除。

> **v0.2.0/v0.2.1 升级提醒：** 这些版本的应用内更新器在备份 `app.asar` 时会稳定失败，旧客户端不能通过下载新版本修复正在运行的旧更新器。房主和每位成员都必须手动下载 v0.2.2 或更新版本的 Setup，并在原安装目录覆盖安装一次；不要先卸载或删除用户数据。完成这一次后，才使用修复后的客户端进行后续应用内更新。

## 创建和加入房间

### 房主创建房间

1. 打开 Agent Hub，选择“创建房间”。
2. 选择本机 Git 项目目录，填写房间名称、项目名称和默认分支。
3. 创建后打开“连接设置”，把邀请地址和房间码发给协作成员。
4. Windows 防火墙询问时，只在可信的专用网络中允许访问。
5. 开发期间保持 Agent Hub 运行。关闭主窗口后可留在系统托盘；彻底退出或关机会让房间离线。

邀请地址通常类似 `http://192.168.1.10:4173`，以界面显示为准。当前局域网 HTTP 模式不能直接暴露到公网。

### 成员加入房间

1. 每位成员先在自己的电脑上准备同一个 Git 项目的本地仓库，本地路径可以不同。
2. 打开 Agent Hub，选择“加入房间”，选择本地项目目录。
3. 填写房主提供的邀请地址、房间码和自己的显示名称。
4. 加入后会立即读取房间已有的成员、工作范围、风险、决定、验证和功能记忆索引，不是只能看到加入后的新记录。

房间码只提供 Agent Hub 房间访问权，不会赋予 GitHub 仓库写权限。GitHub 协作者、分支保护和 Pull Request 权限仍需在 GitHub 单独配置。

同一台电脑可以保存多个房间，也可以让多个房间指向同一个本地项目，但一个规范化本地仓库同一时间只能有一个活动房间。打开其中一个房间时，Agent Hub 会先暂停同项目的旧房间接入，再启用所选房间；路径别名、大小写差异和可解析的链接不会被当成不同项目。旧房间暂时离线时，本机暂停仍立即生效，远端会话或租约清理以警告形式延后，不会仅因网络故障阻止所选房间或 Codex 写入。

## 连接 Codex：MCP 与 Hooks

每位成员加入房间后都要在自己的电脑上完成一次连接：

1. 在 Agent Hub 中打开“连接设置”。
2. 点击“安装连接”。程序会备份现有 `~/.codex/config.toml`，再写入一个房间专用 MCP 配置和五类 Hook。
3. 完全退出并重新启动 Codex。
4. Codex 首次加载非托管 Hook 时会要求用户审核。核对命令指向已安装的 Agent Hub 后，信任 `SessionStart`、`PreToolUse`、`PostToolUse`、`Stop` 和 `SessionEnd` 五项。
5. 从已连接的本地项目目录创建 Codex 任务。项目外的无项目任务不会自动匹配该房间。

MCP 与 Hook 分工如下：

| 组件 | 作用 |
| --- | --- |
| MCP | 按需查询房间上下文、功能记忆和协调状态，并登记会话内批准等操作 |
| `SessionStart` | 打开房间会话，注入预算内的实时状态和相关功能索引 |
| `PreToolUse` | 在 Agent 写入前识别目标路径和符号，检查租约、风险策略和历史功能影响 |
| `PostToolUse` | 只登记能够归因到本次 Agent 工具调用的实际变化，更新本地诊断和房间状态 |
| `Stop` | 回合结束后停止自动租约续期；归因改动已提交或完全撤销时释放，否则保护到租期到期 |
| `SessionEnd` | 汇总可归因改动和 Git/验证证据，形成候选功能修订并结束当前会话 |

成员凭证由 Windows DPAPI 加密后保存在本机，不会写入项目仓库或 Codex 配置。不要把一名成员的连接数据复制给其他人。

“退出房间”只暂停本机接入并保留历史记录；“从本机移除”则删除该房间的本机保存记录、加密成员凭证、Hook 会话和本地接入状态，但不会解散远端房间或删除团队记录。移除时只清理名称、命令、完整参数和 `--connection-id` 都与该连接精确匹配的 `agent_hub_*` MCP 条目；其他房间、用户修改过的配置和非 Agent Hub 配置会保留。只有最后一个可识别的 Agent Hub MCP 条目被移除时，程序才尝试删除仍与受管命令精确匹配的共享 Hook，并在实际改写配置前创建备份。配置发生变化后需要重启 Codex。

### 退出、托盘与本机接入状态

v0.2.1 将“关闭窗口”和“停止 Agent Hub 后台”明确分开；v0.2.2 进一步区分“暂停连接”和“从本机删除记录”：

| 操作或状态 | 本机 Hook/MCP | 远端会话与租约 | 数据 |
| --- | --- | --- | --- |
| 退出房间 | 只暂停所选连接；以后重启仍保持暂停，直到重新启用 | 立即尝试关闭房间服务器首次处理暂停时可见的本人会话、释放本人全部活动租约，并取消相关申请 | 保留成员身份、加密凭证、房间历史、设置和功能记忆 |
| 从本机移除房间 | 永久删除该连接的本机接入状态；精确清理对应 Codex MCP 配置 | 在线时先尝试清理本人状态；临时离线时本机删除仍完成，远端状态可能等待过期 | 删除本机连接与加密凭证；远端房间、团队记录和房主数据库保留 |
| 关闭主窗口 | 窗口隐藏到系统托盘，接入继续工作 | 不清理、不释放 | 全部保留 |
| 托盘“退出” | 先让全部本机连接的 Hook/MCP 失效，再停止后台 | 尝试清理本人会话和租约；存在未到期完成任务的连接保留远端状态，重启后继续检查提交或等待 TTL | 全部保留 |
| 房主退出 | 先清理房主本人状态，再停止本机房间服务 | 其他成员暂时离线；不会删除房间 | SQLite 数据库和历史保留 |
| 安装更新 | 进入 `maintenance`，Hook/MCP 暂停 | 不释放会话和租约 | 更新失败回退后恢复接入 |
| 程序崩溃或进程被结束 | 运行哨兵失效后，Hook/MCP 自动静默停用 | 不承诺远端自动释放手动独占租约 | 数据保留，普通租约仍按服务端租期规则处理 |

桌面后台约每 5 秒原子刷新一次运行哨兵。哨兵缺失、损坏、记录的 PID 已退出，或心跳超过约 30 秒未更新时，本机接入视为 inactive。inactive 的 Hook 完全静默：不连接房间、不创建会话、不注入上下文、不提示冲突，也不阻止写入。

MCP bridge 先完成本地握手，仅在 Codex 请求工具时懒连接房间。连接暂停或房间暂时不可用时返回空工具列表，不建立远端连接；恢复后自动重新连接并刷新工具列表。

退出清理使用幂等请求。`cutoffAt` 是客户端生成的请求身份参数，实际清理边界由房间服务器在首次处理该请求时用自己的时钟确定，避免两台电脑时间不一致导致漏清或误清。网络暂时不可用时，本机接入仍立即停用，未完成的清理进入本地重试队列；等待期间 Hook、MCP、后台扫描和桌面写请求都不会创建新的远端状态，清理成功后才自动恢复，因此旧请求不会误关恢复后新建的会话或租约。网络超时、断网、HTTP 5xx 属于软失败，Codex 写入不会仅因为房间暂时离线而被阻塞，但会显示黄色诊断；真实租约冲突、会话冻结、认证失败或本机凭证损坏仍按明确的阻塞或错误处理。

升级后如果旧连接文件异常地为同一规范化仓库留下多个活动房间，Agent Hub 会在启动时把这些候选全部暂停，等待用户明确打开目标房间。若仍检测到歧义，Hook 会允许本次写入并提示本次没有完成跨成员协作检查；后台扫描和通知也会跳过该仓库，而不是任意选择一个房间或错误阻塞写入。

v0.2.3 沿用协议版本 1，数据库 schema 升至 4，并继续使用 Codex 配置中的稳定 Hook launcher 路径。升级后只对已经明确安装过的 Agent Hub 接入校正受管 MCP 与五类 Hook，用户 Hook 和其他 MCP 保持不变。

## 日常工作流程

连接完成后，成员正常在 Codex 中开发即可：

1. 会话开始时，Agent Hub 返回实时租约、当前规则、未解决高风险和少量相关功能索引。
2. Codex 规划任务时，MCP 根据任务目标、路径、系统、类、方法、接口、测试和依赖关系检索最相关的功能记忆。
3. Agent 准备写入时，Hook 自动领取尽可能小的工作范围，并按具体文件重新判断风险。
4. 黄色警告会记录重叠和原因，但不阻止写入；红色阻塞会暂停写入并自动创建释放申请。
5. 如果目标影响已经完成的功能，Codex 会列出受影响行为、符号和路径，只有当前成员明确确认后才能在批准范围内继续。
6. 写入后只检查本次工具调用可归因的变化。人工编辑、IDE 或 Unity 的外部变化不会被登记为 Agent 风险。
7. Codex 回合结束后停止续租自动工作范围。归因改动已完整提交或完全撤销时立即释放；仍有未提交改动时继续保护到房间租期到期，后台每 15 秒检查一次是否已经提交。
8. `SessionEnd` 保存可追溯的 Git 与验证证据并关闭 Agent Hub 会话。证据不足的功能修订保持草稿或候选状态，等待提交的自动保护独立保留到提交完成或租期到期。

Agent Hub 只检查当前 Codex 任务已归因路径是否完整进入本地分支 HEAD，不会代替成员执行 `git commit` 或要求 `push`。无关提交、部分提交、提交后继续修改、分支变化和证据不完整都不会提前释放；继续同一任务写入时会恢复或重新领取自动保护。手动普通和独占租约不受这套自动释放流程影响。

## 风险策略

每次重叠都按具体项目相对路径计算。v0.2.1 沿用以下默认策略：

| 文件范围 | 默认结果 |
| --- | --- |
| 普通源码 | 黄色警告 |
| Unity 场景和 Prefab | 红色阻塞 |
| Unity 序列化资源与 `.meta` | 红色阻塞 |
| `ProjectSettings`、包清单等项目设置 | 红色阻塞 |
| Git/CI 配置 | 红色阻塞 |
| JSON、YAML、XML、表格等结构化配置 | 红色阻塞 |
| Luban 源表、生成文件和相关目录 | 黄色警告 |
| 整个仓库范围 | 红色阻塞 |
| 其他未分类文件 | 黄色警告 |

房主可按预设分类、扩展名、具体文件或项目相对目录改成黄色或红色。匹配优先级为：具体文件、最长匹配目录、扩展名、预设分类；每次保存形成新的策略版本并记录操作者和时间。

房主还可关闭“关键范围阻塞保护”。关闭后，自动租约和普通工作范围的重叠全部降为黄色警告；这不会删除租约，也不会绕过手动独占租约或历史功能修改确认。其他成员只能查看，不能修改该开关和风险策略。

## 功能记忆与修改确认

功能完成时，Agent Hub 会结合任务目标、实际写入路径、代码符号、Git 基线与提交、依赖关系、测试结果和剩余风险，形成结构化功能修订。每条修订不可变，并标明新增、扩展、替代、废弃、回滚或冲突关系。

- 普通查询只读取每项功能的“当前有效版本”。
- 未提交、验证失败或证据不足的修订保持草稿、候选或待验证状态，不替换稳定版本。
- 同一成员后来修改同一系统，不会按“时间最新”覆盖整个系统；只更新实际受影响的功能和行为契约。
- 不同分支对同一行为产生互斥修改时保留双方候选，等待合并或明确确认，不按时间自动选胜者。
- 回滚会创建新的回滚修订，旧版本仍保留用于审计。

上下文采用分层加载：启动时只给索引摘要；规划时返回少量相关记忆卡；确认相关后再按需加载行为、约束、符号、测试或历史证据。这样不会在每次任务开始时把全部房间历史塞给 Codex。

当写入触及已记录的方法、公开接口、行为契约、关联测试或无法排除影响的 Unity 资源时，Hook 会先阻止本次写入。Codex 必须在当前对话中说明影响并询问当前成员。确认只绑定当前会话、功能版本、符号和路径；用户拒绝、没有明确回答或范围变化时，不得继续修改原功能。

## 释放申请与租期

红色阻塞会自动创建一条去重、持久化的释放申请，并通知冲突租约的持有人：

- Agent Hub 运行或位于托盘时，通过 Windows 通知和应用内待处理窗口提醒。
- 持有人可交出范围、暂不释放或查看详情；离线不会被视为同意。
- 普通租约批准后，只原子交接发生冲突的路径，其他路径继续保留。
- 黄色警告不会创建申请。

自动租约默认在停止心跳 10 分钟后到期。房主可选择 5、10、15、30 或 60 分钟；持续工作的 Agent 通过心跳续期。桌面端只为最近 5 分钟内发生过真实 Hook 活动的普通会话保活；正在执行的单次写入可在构建、测试或 Unity 运行期间继续保活，但最长 2 小时。超过上限后停止续期，由房间租期自然过期，避免异常退出的 Codex 永久占用范围。设置变化作用于新租约和下一次续期，不会突然截短已经领取的有效租约。

## 手动独占租约

成员需要明确保护某个文件或目录时，可创建固定到期的手动独占租约：

- 最短 5 分钟，最长时间由房主设置，默认上限为 24 小时。
- 独占租约不会被 Agent 心跳自动延长，需要租客主动续租。
- 其他成员的 Agent 无论目标文件默认属于黄色还是红色分类，都必须先取得租客批准。
- 房主关闭普通红色阻塞也不会削弱独占租约。
- 租客批准释放申请时，整份独占租约结束；申请人只取得自己实际请求的范围。
- 独占租约只约束已接入 Hook 的 Agent，不能锁住键盘、IDE、Unity 或其他人工操作。

## 人工与外部变化

Agent Hub 只对能够可靠归因到当前 Agent 工具调用的写入执法。成员手工编辑、IDE/Unity 自动保存和无法归因的外部变化：

- 不创建租约；
- 不生成房间黄色警告、红色阻塞或风险；
- 不触发当前 Agent 会话隔离；
- 只在本机保留必要的临时诊断。

这些变化仍属于用户已有工作，Agent 不得擅自覆盖、删除或回滚。如果人工和 Agent 同时修改同一个明确目标文件，系统无法可靠按行区分来源，该文件仍按 Agent 写入规则检查，并要求 Agent 保留已有用户改动。Agent 自己发出的写命令如果无法识别真实目标，会在执行前停止，不能伪装成外部变化绕过保护。

## 自动更新与数据保留

从 v0.2.0 开始，Setup 客户端在启动后和运行期间自动检查 `lcx040126/agent-hub` 的 GitHub Releases。发现新版后显示版本、说明和大小，由本机用户点击后下载、校验、安装并重启，不会在工作中擅自重启。

更新会校验固定 GitHub HTTPS 来源、签名清单、协议/数据库兼容范围、文件大小和 SHA-256，并拒绝降级或被篡改的安装包。应用内更新会一致性备份 SQLite 房间数据库；连接配置和 DPAPI 凭证位于安装目录之外，不会由安装器主动覆盖。v0.2.2 的恢复准备使用 Electron 的物理文件系统复制安装目录，并校验备份 `app.asar` 的大小和 SHA-256，避免把复制目标误当作虚拟 ASAR 目录。恢复守护成功布防后，新版本启动健康检查失败时使用上一份可恢复安装和数据库备份回退。新版本确认健康后，才清理不再需要的更旧安装缓存和临时备份。

### v0.1.0 到 v0.2.0 必须手动升级一次

v0.1.0 没有完整客户端更新器，所以房主和每位成员都必须从 v0.2.0 Release 手动下载 Setup 安装包并覆盖安装一次。不能等待 v0.1.0 自动升级。

建议先停止新的 Agent 写入，由房主先升级并确认原房间可打开，再让成员逐台升级。不要卸载后清除用户数据，也不要手工删除房间数据库。

### v0.2.0 或 v0.2.1 到 v0.2.2 必须手动覆盖一次

v0.2.0 和 v0.2.1 的更新恢复代码使用 Electron 改写过的 `node:fs` 递归复制安装目录。复制目标路径到达 `resources/app.asar` 时，Electron 会把尚未形成有效归档的目标当作 ASAR 解析，并抛出 `Invalid package`。失败发生在恢复计划写入和安装器启动之前，与 Codex 是否退出、源 `app.asar` 是否损坏或安装目录是否在 D 盘无关。

该缺陷存在于正在执行更新的旧客户端中，因此 v0.2.2 发布后仍必须手动下载并运行 `AgentHub-Setup-0.2.2-x64.exe`，选择原安装目录覆盖安装。不要等待 v0.2.0/v0.2.1 在应用内完成这次升级，也不要通过卸载并清空数据来规避。覆盖完成并确认房间、连接和 Codex 配置仍在后，后续版本才由修复后的客户端继续检查和安装。

覆盖安装和后续更新的目标是保留房间数据库、成员与项目连接、加密凭证、房间设置、协作记录、功能记忆、租约和待处理申请。v0.2.0 的历史验证结果见 [v0.2.0 发布说明](docs/releases/v0.2.0.md)，生命周期隔离见 [v0.2.1 发布说明](docs/releases/v0.2.1.md)，本机恢复修复见 [v0.2.2 发布说明](docs/releases/v0.2.2.md)，Stop 与提交后释放、持久化收尾及升级配置校正见 [v0.2.3 发布说明](docs/releases/v0.2.3.md)。

## 对 Git 的影响

Agent Hub 不安装本地 commit/push Hook，不会修改提交、自动合并、回滚或推送代码。成员仍照常使用 `git add`、`git commit`、`git pull`、`git push` 和 Pull Request。

可选的 `gate:publish` 可在 CI/Release 阶段检查房间中已登记的阻塞冲突、未解决 critical 风险和最新失败验证。正式 Release 未配置房间门禁时，仓库必须显式设置 `AGENT_HUB_ALLOW_UNGATED_RELEASE=true` 才能发布，避免因漏配而静默绕过。它只影响远端检查结果，不改变本地 Git 操作，也不能替代测试、代码审查和分支保护。

## 能力边界与安全

- Agent Hub 能降低耦合系统被意外改坏的概率，但不能证明业务语义绝对兼容。
- Git、源码、Luban 源表、人工批准的项目规则和真实测试结果仍是最终事实来源。
- 只有正确加入房间、安装并信任 Hook 的 Agent 才受自动保护。
- 当前 HTTP 房间只适合可信局域网，不要通过端口映射直接暴露到公网。
- 房间默认同步结构化元数据，不上传源码全文、补丁、密钥、环境变量、私人提示词或模型隐藏思考。
- Windows 通知只是提醒入口，申请和租约的最终状态以房主服务中的持久化记录为准。

完整产品规则与协作边界见 [rule.md](rule.md)。

## 开发与构建

需要 Node.js 22.13 或更高版本，以及 pnpm 11。

```powershell
pnpm install
pnpm dev
pnpm typecheck
pnpm test
pnpm build
pnpm desktop:pack
```

`pnpm desktop:pack` 只生成 Windows x64 NSIS 安装包。推送与 `package.json` 版本一致的 `v*` 标签后，Release workflow 会执行类型检查、测试、打包、签名更新清单、生成 SHA-256 文件，并把资产上传到 Draft Release；人工核验发布说明和六项资产后再公开。

## 项目结构

```text
src/client/       桌面工作台界面
src/desktop/      Electron 主进程、安装接入、更新和恢复
src/companion/    本地扫描、MCP bridge、Codex Hook 和写入归因
src/server/       房间协议、SQLite、风险策略、租约与功能记忆
src/shared/       公共协议与版本信息
docs/             架构、接入和发布资料
```
